# Ручне звільнення товару від карантину

Пункт 13 реалізовано в тестовій гілці. Приймання в Google Ads/Sheets ще не проведено.

## Як користуватися

1. Після звичайного запуску відкрийте ProductDiagnostics і знайдіть товар за id.
2. Увімкніть checkbox quarantine_exempt: він означає «Не застосовувати карантин».
3. Виконайте наступний звичайний запуск. Товар звільняється від активного карантину й не потрапляє під жодне з чотирьох правил.
4. Зніміть checkbox, щоб наступний звичайний запуск знову застосував штатні перевірки.

Типове значення — false. ID та звичайний Funnel Stage зберігаються. Категорійні й сезонні виключення продовжують діяти. Увімкнення checkbox саме по собі не оновлює Merchant: потрібні звичайний запуск, запис Products та обробка допфіда.

## Історія та дати

Звільнення реально активного товару записує дату виходу через чинний lifecycle один раз. Для неактивного товару перемикання checkbox не створює дату виходу, історію або нове відсікання статистики. Наявна справжня дата виходу зберігається. Після зняття checkbox правила використовують звичайні періоди й цю дату; штучного нового старту немає.

Лічильники не скидаються. Історія вже відомих товарів із checkbox зберігається додатково до quarantine_log_max_rows, тому журнал може перевищувати цей ліміт. Порожні записи історії не створюються. Після зняття checkbox діє звичайне обмеження журналу; checkbox не відновлює історію, яку було втрачено раніше. Явний reset_quarantine зберігає свій зміст — очищення карантинного стану та історії; ручний checkbox не очищається.

## Збереження ручного значення

Значення читається за normOfferId_, незалежно від enable_previous_state_read і повного запису ProductDiagnostics. Повна, часткова та мінімальна актуалізація зберігають його за ID. Порядок рядків не визначає відповідність. За дубльованого нормалізованого ID будь-яке true означає звільнення; перед скасуванням приберіть усі галочки цього ID.

Checkbox додається праворуч від наявних колонок. Внутрішні outputRows та індекси аналітики не розширюються; Dashboard зіставляє колонки за заголовками. Невідомі користувацькі колонки та формули не очищаються, але їхні значення залишаються у власних фізичних клітинках: вони не переносяться за ID.

Окремого сховища немає. Якщо повна регенерація видалила рядок товару, якого більше немає в каталозі, його checkbox втрачено. При поверненні товару значення буде false. За мінімального запису старий рядок і його checkbox залишаються, доки рядок присутній.

Dashboard-only враховує checkbox у відображенні карантину зі збереженої діагностики, але не звільняє реєстр і не перераховує товарні метрики. Для звільнення й актуального допфіда потрібен звичайний запуск. За часткової/вимкненої діагностики інші діагностичні поля можуть залишатися старими.

Власний захист скрипта додає колонку checkbox до дозволених для редагування діапазонів, зберігаючи попередні винятки. Чужий захист не змінюється. Якщо enable_sheet_protection=false, наявні старі захисти не оновлюються: доступ до checkbox може потребувати дії власника таблиці.

## Перевірка перед прийманням

Локальний tests/quarantine-exempt.cjs перевіряє всі чотири правила, справжній/відсутній вихід, повторний запуск, скасування, лічильники, обмежений журнал, ID і Funnel Stage, інші виключення, порядок рядків, повний/частковий/мінімальний запис, Dashboard, сторонні формули й діапазон редагування.

У погодженій тестовій таблиці повторіть ці сценарії для активного й неактивного товару. Звірте Registry, History, дату виходу, Products і Dashboard. Окремо перевірте редагування checkbox обліковим записом користувача, перестановку ID та обидва вимкнені перемикачі читання попереднього стану/повної діагностики. Локальні mocks не підтверджують поведінку живого SpreadsheetApp. Таблицю для цього тесту ще не надано.
