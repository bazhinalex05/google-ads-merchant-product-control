# Unified Merchant Product Control - ожидаемая логика работы скрипта

Статус: ожидания пользователя от работы скрипта. Документ дополняется по согласованным требованиям; это не описание фактической реализации.

Назначение документа: сохранять ожидания пользователя как основу дальнейшей работы. Фактическая реализация описана в [технической документации](../technical-reference.md).

## Диктовка пользователя

### Обязательные условия работы скрипта

Лист `Products` является допфидом и всегда должен быть первым листом таблицы.

На листе `Products` всегда должны быть товары. Если в Merchant настроено автообновление допфида, Merchant в любой момент может забрать этот лист. Если товаров на листе не будет, вся цепочка, которую настраиваем в таблице, сломается.

То, что можно сделать формулами в таблице, чтобы не нагружать скрипт и не уходить в timeout, нужно делать формулами.

Если таблица начинает ломаться или уходить в timeout из-за перегруза формулами, тогда эту часть нужно переносить в скрипт.

Листы `ProductTypes` и `Seasonality` должны быть резиновыми. Они должны учитывать, что у клиента может меняться структура сайта, структура каталога и количество товаров.

Если клиент проставил галочки, они должны соответствовать конкретному ID товара или конкретной категории. Галочки не должны жить своей жизнью и не должны съезжать на случайные строки на `ProductTypes` или `Seasonality`.

Все boolean-поля, которые отображаются в таблице как флажки, должны быть именно флажками. То, что нажимается руками, и вообще все флажки в таблице должны оставаться checkbox-ячейками. Текстовых значений `TRUE` или `FALSE` в таблице быть не должно ни при каких обстоятельствах.

На листе `Settings` все настройки должны быть разбиты на логические блоки, чтобы листом было удобно пользоваться.

Обязательные поля и поля, которые нужны при каждой новой настройке проекта, должны подсвечиваться красным в ячейке с названием настройки.

Ячейки со значениями, которые заполняются вручную, должны подсвечиваться жёлтым, как сейчас на `Settings`.

Все комментарии в таблице должны быть только на украинском языке.

На листах `ProductTypes` и `Seasonality` все ячейки, которые заполняются вручную, должны подсвечиваться жёлтым:

- ячейки с галочками;
- ячейки с комментариями;
- ячейки, где клиент должен что-то написать.

### Общая логика сбора данных

Скрипт должен подключаться к API и собирать данные по каждому товару, который есть в Merchant Center.

По каждому товару нужно собрать:

- ID товара;
- количество кликов;
- количество показов;
- product type;
- количество конверсий.

Чтобы не анализировать все фиды, если это не нужно, в скрипте должна быть настройка с выбором фидов.

### Ограничение по фидам

У клиента может быть несколько разных фидов.

В скрипте обязательно должна быть настройка, из какого фида или фидов тянуть товары. Эта настройка сейчас есть и должна сохраняться.

В настройке можно через запятую указать ID фидов, с которыми работает скрипт.

Скрипт должен анализировать только товары из выбранных фидов:

- все ID товаров из указанных фидов попадают в анализ;
- товары из остальных фидов не должны попадать в анализ;
- к остальным фидам скрипт не должен обращаться при работе через API, чтобы экономить время выполнения.

### Категории и product type

У каждого клиента на новом сайте или интернет-магазине есть каталог: категории, подкатегории и фильтры. Скрипт должен знать, где лежит каждый товар.

Помимо статистики по показам, кликам и продажам, скрипт должен собирать цепочку категории товара.

Возможные варианты источника цепочки категорий:

1. Цепочка автоматически передаётся в стандартный `product_type`.
   В этом случае скрипт получает её через Merchant API из `product_type`.

2. В оригинальном фиде в `product_type` лежит неправильная или непригодная цепочка, как часто бывает на Prom.ua.
   В этом случае правильная цепочка может загружаться через дополнительный фид и уже в Merchant заменять или дополнять исходное значение.
   Скрипт должен читать итоговые данные из Merchant, а не стучаться в оригинальный фид сайта, потому что в Merchant уже происходит матчинг основного фида и дополнительного фида.

3. Правильная цепочка передаётся клиентом или программистом в другое место.
   Она может лежать в custom label, в нестандартном атрибуте, который Merchant напрямую не знает как стандартный, или в отдельном дополнительном фиде.
   Скрипт должен быть готов принимать такую цепочку.

Пример: product type можно читать из `custom_label_2`, если правильная цепочка категорий передаётся туда.

Эти варианты должны быть предусмотрены настройками скрипта. По версии пользователя, такие настройки уже были заложены, но нужно отдельно проверить, насколько корректно они сейчас работают.

### Дерево ProductTypes и включение категорий

После получения цепочки категорий скрипт должен добавить её в таблицу и построить дерево категорий на листе `ProductTypes`.

Клиент должен иметь возможность поставить галочку напротив нужной категории в дереве.

Логика включения:

- категории с включённой галочкой идут в показы;
- товары из категорий без включённой галочки должны получать `excluded_destination`;
- для исключения используются два значения: `Shopping Ads` и `Display Ads`;
- пока клиент не выбрал категорию, товары из этой категории должны быть выключены.

На старте проекта на листе `ProductTypes` все категории должны быть включены по умолчанию, чтобы можно было быстро установить скрипт и сразу работать без ручной разметки всего дерева.

### Наследование галочек в дереве категорий

Дерево категорий состоит из уровней `product_type_l1`, `product_type_l2`, `product_type_l3` и так далее.

Если клиент ставит галочку только напротив категории верхнего уровня и не ставит более точные галочки ниже, то в показы должны идти все товары внутри этой категории и всех её подкатегорий.

Если внутри отмеченной верхней категории клиент дополнительно отмечает только одну конкретную подкатегорию, то в показы должна идти:

- сама отмеченная верхняя категория и товары, которые лежат прямо в ней;
- отмеченная подкатегория;
- товары внутри отмеченной подкатегории.

Остальные неотмеченные подкатегории внутри этой верхней категории не должны идти в показы и должны получать `excluded_destination`.

Если клиент отмечает категории нижнего уровня и одновременно отмечает одну категорию среднего уровня, то в показы должны идти:

- все отмеченные категории нижнего уровня;
- отмеченная категория среднего уровня;
- товары, которые лежат прямо в отмеченной категории среднего уровня, если такие есть.

Все остальные неотмеченные ветки этой части дерева должны игнорироваться и получать `excluded_destination`.

Общее правило: любая отмеченная категория на любом уровне становится выбранной веткой, даже если её родительская категория выше по дереву не отмечена. Если ниже в этой выбранной ветке нет более точных отмеченных категорий, работает наследование на всё поддерево этой ветки. Если ниже в этой ветке есть более точный выбор, показываются только отмеченные нижние ветки и товары, которые лежат прямо в отмеченных родительских категориях. Неотмеченные соседние ветки внутри выбранной части дерева должны получать `excluded_destination`.

Если категория верхнего уровня не выбрана, а внутри во вложенности стоят галочки на категориях второго уровня или ниже, эти вложенные галочки должны работать. В этом случае выбранные вложенные категории становятся рабочими ветками.

### Расчёт Funnel Stage по всему ассортименту

После сбора данных скрипт должен определить сегмент, к которому относится каждая товарная позиция.

Для расчёта funnel stage скрипт должен:

- иметь данные по показам по всему ассортименту;
- провести среднюю черту по показам;
- товары ниже этой черты относить к низким показам;
- товары выше этой черты относить к высоким показам;
- по такой же механике провести разделение по кликам.

Комбинации кликов и показов формируют этапы воронки:

- высокие клики и низкие показы = `вк+нп`;
- высокие клики и высокие показы = `вк+вп`;
- остальные этапы формируются как комбинации низких/высоких кликов и низких/высоких показов;
- если у товара есть продажи, он относится к этапу `продажі`;
- если у товара нет продаж и нет показов, он относится к этапу `6 без стат`.

В результате товару присваивается funnel stage.

### Расчёт внутри benchmark-групп

Расчёт по всему ассортименту недостаточен, потому что у клиента могут быть разные категории и разные приоритеты.

Пример проблемы: категория A может иметь выраженную сезонность и высокую активность, а категория B может иметь слабую текущую активность. Если считать всё вместе, товары категории A будут попадать в высокие клики и высокие показы относительно категории B. Но по приоритетам клиента может быть нужно активнее продвигать категорию B.

Поэтому нужен ограничитель, который позволяет считать funnel stage отдельно внутри группы. Для этого используется benchmark label: он объединяет товары в группы, и funnel stage рассчитывается внутри каждой такой группы.

Benchmark label может отражать категории, приоритеты или другие рамки ассортимента, внутри которых надо сравнивать товары.

### Приоритеты и передача в Merchant

Benchmark label и priority label должны быть разными сущностями.

Benchmark label определяет рамку, внутри которой скрипт считает клики, показы и funnel stage.

Priority label определяет группу товаров, которую нужно передать в Merchant, чтобы затем создать по ней группу товаров в Google Ads, распределять деньги, запускать трафик и создавать объявления.

Пример:

- несколько категорий, например бигуди, бритвы, ножницы, одежда парикмахеров и расчески, могут входить в один общий benchmark `волосы`;
- внутри benchmark `волосы` скрипт рассчитывает funnel stage только среди товаров этого benchmark;
- категории из других benchmark-групп не должны участвовать в этом расчёте;
- товары без заданного benchmark попадают в benchmark-группу `other`, которая считается отдельно;
- внутри этих же товаров можно отдельно назначить priority `пріоритет 1` для бритв и ножниц;
- позже можно назначить priority `пріоритет 2` для одежды парикмахеров, принадлежностей и расчесок;
- у priority тоже должна быть группа `other` для товаров без приоритета.

Benchmark нужен для расчёта.

Priority нужен для управления деньгами и структурой продвижения.

Приоритеты нужно передавать в Merchant, чтобы по ним можно было создать группы товаров в Google Ads.

Benchmark label не нужно передавать обратно в Merchant. Он нужен для настройки расчёта, чтения скриптом и диагностики.

Benchmark label должен быть видимым по каждому товару в рабочей диагностике или другом отдельном листе, чтобы можно было проверить, к какому benchmark относится конкретный товар.

Передавать benchmark как атрибут в Google Ads / Merchant нет необходимости.

Для funnel stage уже есть отдельная метка, куда скрипт записывает рассчитанный этап.

Для benchmark отдельную custom label метку занимать не нужно.

Для priority отдельная custom label метка нужна, потому что priority должен передаваться в Merchant.

В таблице должны быть две отдельные настройки:

- из какого поля читать benchmark label для расчёта;
- в какое поле писать priority label для передачи в Merchant.

Текущая ситуация, где есть только одна настройка `benchmark_label_field`, недостаточна и смешивает две разные задачи.

### Карантин

У скрипта должно быть три вида карантина.

Каждый карантин должен приводить к паузе товара через `excluded_destination`.

Для каждого вида карантина срок паузы должен настраиваться отдельно.

Периоды проверки карантина могут отличаться от периода, по которому скрипт считает клики и показы для funnel stage. Период карантина может быть больше или меньше периода funnel stage.

#### 1. Клики без продаж

Скрипт проверяет выбранный период по каждому товару.

Если за этот период:

- у товара было заданное вручную количество кликов;
- у товара не было продаж;

то товар ставится на паузу через `excluded_destination`.

Период проверки задаётся отдельно в настройках.

Порог количества кликов задаётся вручную.

Срок карантина задаётся отдельно.

#### 2. Перетраты относительно цены товара

Скрипт проверяет выбранный период по каждому товару.

Если товар потратил слишком много относительно своей цены и не дал достаточной рекламной отдачи, его нужно поставить на паузу через `excluded_destination`.

Период проверки задаётся отдельно в настройках и может отличаться от периода funnel stage.

Порог задаётся в процентах относительно цены товара.

Пример: если у товара ноль конверсий, товар потратил 100 грн, а цена товара 50 грн, такую товарную позицию нужно поставить на паузу.

Срок карантина задаётся отдельно.

#### 3. Дорогой клик

Дорогой клик всегда проверяется только за вчерашний день.

Причина: скрипт может получить из API только средний CPC, а не отдельные клики. Поэтому большой период для этого правила использовать нельзя.

Настройка периода `0` в этом контексте означает проверку вчерашнего дня.

Порог дорогого клика задаётся вручную.

Срок карантина задаётся отдельно.

### ProductDiagnostics как объяснение решений скрипта

Лист `ProductDiagnostics` должен показывать по каждому товару всю информацию, которую скрипт использовал для принятия решений.

По любому ID товара в `ProductDiagnostics` должно быть видно:

- к какому benchmark относится товар;
- какой priority назначен товару;
- какой funnel stage присвоен товару;
- какие клики, показы, конверсии и другие метрики использовались для расчёта funnel stage;
- какие пороговые значения кликов и показов действовали внутри benchmark-группы товара;
- какие данные использовались для каждого карантинного правила;
- почему товар получил или не получил `excluded_destination`.

Для funnel stage должны быть видны данные за период расчёта funnel stage, например 14 дней:

- клики;
- показы;
- конверсии;
- другие используемые метрики.

Для benchmark-группы должны быть видны пороги:

- сколько кликов нужно для попадания в верхнюю часть по кликам внутри benchmark;
- сколько показов нужно для попадания в верхнюю часть по показам внутри benchmark.

Это нужно, чтобы можно было объяснить клиенту, почему товар попал в конкретный сегмент. Например: товар относится к определённому benchmark, за период получил мало показов относительно порога этого benchmark, поэтому попал в конкретный funnel stage.

Для карантина должны быть видны данные за отдельные периоды проверки каждого карантинного правила:

- для карантина `клики без продаж` должны быть видны клики и конверсии за период проверки этого правила, например 30 дней;
- для карантина `перетраты относительно цены` должны быть видны расходы, цена товара, конверсии и процент/порог перетраты за период проверки этого правила;
- для карантина `дорогой клик` должен быть виден средний CPC за вчерашний день и ручной порог дорогого клика.

Если период карантина отличается от периода funnel stage, в `ProductDiagnostics` должны быть видны оба набора данных: отдельно данные funnel stage и отдельно данные карантина.

### Листы карантина

У скрипта должно быть два листа для карантина.

Конкретные названия листов не принципиальны. Важны две разные роли:

- лист текущего карантина;
- лист исторического карантина.

#### Лист текущего карантина

Лист текущего карантина должен показывать товары, которые находятся в карантине прямо сейчас.

На этом листе не должно быть лишних товарных позиций, которые сейчас не находятся в активном карантине.

Главная функция листа: в любой момент быстро ответить клиенту:

- какие товары сейчас на паузе;
- по какой причине они на паузе;
- когда они выйдут из карантина.

#### Лист исторического карантина

Лист исторического карантина должен хранить список товаров, которые когда-либо попадали в карантин.

На этом листе должен быть счётчик, сколько раз конкретный товар попадал в карантин.

Назначение листа:

- видеть проблемные товарные позиции исторически;
- понимать, какие товары регулярно возвращаются в карантин;
- иметь возможность после переустановки скрипта перенести старый список ID товаров, которые уже были в карантине;
- продолжить увеличивать счётчик на единицу при новых попаданиях товара в карантин.

Для этой задачи даты попадания в карантин и подробные причины на историческом листе не обязательны. Важнее иметь ID товара и общий счётчик повторных попаданий.

Исторический лист не должен расти бесконечно, потому что у больших магазинов есть риск раздуть количество ячеек и упереться в лимиты Google Sheets.

Для исторического листа нужен лимит строк. Ориентир: хранить не больше 1000 строк, а лишние старые или менее нужные записи очищать.

### Products как первый лист допфида

Первый лист `Products` должен быть допфидом, который заливается в Merchant.

На листе должны быть:

- ID товара;
- `excluded_destination`;
- funnel stage;
- priority group.

ID и `excluded_destination` может писать скрипт.

Funnel stage можно подтягивать формулой.

Priority group тоже можно подтягивать формулой, чтобы скрипт не тратил на это лишнее время.

Запись данных на этот лист можно делать разными шагами, чтобы таблица не уходила в timeout.

### ProductDiagnostics: нужные данные

`ProductDiagnostics` должен заполняться скриптом из Merchant API, Google Ads и других сервисов, которые использует скрипт.

На этом листе не должно быть бесполезной информации.

На `ProductDiagnostics` нужны:

- ID товара;
- title товара;
- значения `excluded_destination`;
- клики и показы для расчёта funnel stage;
- конверсии для расчёта funnel stage;
- funnel stage;
- клики для первого карантина за период первого карантина;
- конверсии для первого карантина за период первого карантина;
- spend по товару для второго карантина за период второго карантина;
- цена товара для второго карантина;
- конверсии для второго карантина за период второго карантина;
- CPC для третьего карантина;
- product types;
- `product_type_full_path`;
- `product_type_all_paths`;
- `data_source_id`;
- `feed_label`;
- `content_language`;
- сегмент кликов: высокие или низкие клики;
- сегмент показов: высокие или низкие показы;
- benchmark label;
- priority label;
- атрибутированные конверсии и ценность конверсий по прошлому funnel stage.

Период, который используется для расчёта funnel stage, отдельно писать на `ProductDiagnostics` не обязательно.

`product_type_all_paths` должен остаться, потому что он нужен для понимания всех путей product type.

Поля `product_type_source` и `product_type_status` под вопросом: пользователь не понимает, зачем они нужны, нужно проверить техническую необходимость.

Атрибутированные конверсии нужны, чтобы не получать ситуацию, где все конверсии на DashboardData попадают только в этап `продажі`, хотя фактически конверсия могла случиться после того, как товар раньше был в другом funnel stage.

Текущий формат атрибутированных конверсий можно оставить.

### ProductTypes: сохранение ручного выбора

На листе `ProductTypes` клиент выбирает категории галочками.

Выбор клиента должен сохраняться после обновления скрипта.

Категория, которую клиент выбрал, не должна случайно стать выключенной или включённой после следующего запуска.

Сохранение ручных галочек ProductTypes обязательно и не должно ломаться.

### Dashboard и DashboardData

Листы `Dashboard` и `DashboardData` пока не обсуждаются. По ним нужно отдельно принять решение позже.

### Сезонность

Сезонность должна настраиваться клиентом как по категориям, так и по отдельным товарам.

На листе `ProductTypes` должны быть галочки сезонности по категориям.

По умолчанию, если сезонность нигде не размечена, все товары считаются включёнными. Пустые сезонные галочки не должны сами по себе выключать товары, потому что не все клиенты готовы размечать сезонность.

Если сезонные галочки стоят только в одной категории, то эти правила применяются только к этой категории.

Пример: если сейчас активна осень, а у категории или товара стоит галочка только на лето, товар должен получить `excluded_destination` и исключиться на листе `Products`.

Галочки сезонности должны сохраняться при обновлении скрипта.

Если у клиента на сайте появляется новая категория или подкатегория, таблица может расшириться и получить новые строки, но уже проставленные сезонные галочки должны остаться привязанными к своим категориям.

Сезонные галочки на `ProductTypes` должны соответствовать категориям, а не случайным строкам после перестроения дерева.

### Потоварная сезонность

Потоварная сезонность должна иметь приоритет над категорийной сезонностью, если для конкретного товара она задана.

Пример:

- в одной категории есть шорты и штаны;
- шорты зимой не нужны, поэтому по товарам-шортам клиент ставит галочки только на лето;
- штаны нужны и летом, и зимой, то есть круглый год, поэтому по товарам-штанам клиент может не ставить сезонные галочки вообще.

В этом случае:

- для шорт работают потоварные галочки, и они главнее категорийных;
- отсутствие потоварных галочек у штанов не должно выключать их из показа;
- если товарная сезонность задана, она должна переопределять категорийную сезонность;
- если товарная сезонность не задана, товар должен жить по общему правилу: либо по категории, либо считаться включённым, если сезонность нигде не размечена.

### Дополнительные функции, которые нужно описать дальше

Скрипту нужны ещё две важные функции:

1. Дополнительный лист с приоритетами от клиента.
2. Карантин для товаров, по которым есть продажи, но эти продажи безумно дорогие.

Эти два пункта пока зафиксированы как новые обязательные направления. Детальная логика будет надиктована отдельно.

### Лист с приоритетами от клиента

Клиенты часто просят отдельно заниматься приоритетами. Иногда это приоритетные категории, а иногда клиент даёт список конкретных товаров.

Например, клиент может дать список топ-товаров или товаров второго приоритета, которые он считает стабильно продающимися, сезонно важными или просто важными для продвижения. Причина, почему клиент выбрал эти товары, для скрипта не важна. Важно, что эти товары нужно рекламировать отдельно и под них нужно выделять отдельные деньги.

Клиент может передать приоритет двумя способами:

- через категорию;
- через список конкретных ID товаров.

Чтобы не создавать отдельные списки и отдельные допфиды в Merchant, в этой же рабочей таблице должен быть отдельный лист `Priorities` с приоритетными товарами от клиента.

На старте этот лист должен быть пустым.

На листе должны быть минимум две колонки:

- `id`;
- `priority_group`.

Когда клиент даёт список приоритетных товаров, он обычно даёт таблицу в формате: ID товара и какой это приоритет. Этот список можно скопировать и вставить прямо на лист приоритетов.

Скрипт должен читать этот лист и по ID товара присваивать указанную `priority_group`.

После чтения priority group из этого листа:

- значение должно попасть в `ProductDiagnostics` напротив соответствующего товара;
- значение должно попасть на лист `Products` в колонку priority group;
- через `Products` это значение должно попадать в допфид Merchant.

Лист приоритетов от клиента нужен именно для ручных списков ID, которые клиент передаёт отдельно, без создания дополнительного внешнего фида.

Этот лист не должен обновляться, стираться или перезаписываться скриптом. Он должен хранить внесённые вручную приоритеты клиента.

### Карантин для товаров с продажами, но слишком дорогим CPA

Нужен дополнительный карантин для товаров, у которых продажи есть, но эти продажи слишком дорогие.

На листе `ProductTypes` у клиента есть возможность указать `target_cpa` по категории.

Если товарная позиция находится в категории, для которой задан `target_cpa`, и текущий CPA этой товарной позиции превышает этот `target_cpa`, такая товарная позиция должна отключаться через карантин.

У этого карантина должен быть отдельный пул настроек:

- включатель правила;
- период проверки в днях;
- количество дней, на которое товар ставится на паузу;
- порог превышения `target_cpa`, то есть насколько текущий CPA товара должен превышать категорийный `target_cpa`, чтобы товар попал в карантин.

По этому карантину в `ProductDiagnostics` или `DashboardData` должны быть видны соответствующие данные:

- spend товара за период проверки;
- текущий CPA товара за период проверки;
- `target_cpa` категории;
- насколько текущий CPA товара превысил категорийный `target_cpa`.

### Подсветка actual CPA относительно target CPA на ProductTypes

На листе `ProductTypes` есть колонки с информацией по категориям: актуальная CPA и ручной `target_cpa`, который может указать клиент.

При каждом прогоне скрипт должен сверять актуальную CPA категории с её `target_cpa`.

Если актуальная CPA выше, чем `target_cpa`, ячейка актуальной CPA должна подсвечиваться нежно-красным цветом, самым светлым красным.

Если актуальная CPA ниже, чем `target_cpa`, то есть реклама приводит конверсии дешевле целевого CPA, ячейка актуальной CPA должна подсвечиваться зелёным.

### Общий Target CPA, маржа и ROAS по категориям

Для всего сайта нужен общий Target CPA. При этом сохраняется возможность вручную указать Target CPA для конкретной категории на `ProductTypes`: ручное значение категории применяется вместо общего, а если оно не задано, используется общий Target CPA сайта.

Добавляем аналогичный подход для маржи: клиент сообщает общую процентную маржу сайта, при необходимости для конкретной категории можно указать свою маржу. По этой марже автоматически рассчитывается Target ROAS для окупаемости рекламы.

Формула: Target ROAS = 1 / маржа в долях. При марже 30% это 1 / 0,30 = 3,333..., или 333,33% ROAS. Под маржой здесь понимается доля выручки, остающаяся после остальных учитываемых затрат, но до расходов на рекламу, а не наценка.

При одинаковой процентной марже Target ROAS одинаковый для всех категорий. Средний чек меняет допустимую стоимость продажи, но не порог ROAS: при чеке 1 000 грн и марже 30% на рекламу для безубыточности остаётся 300 грн, при чеке 2 000 грн — 600 грн. Это пояснение формулы, а не требование заменить вручную заданный Target CPA расчётным значением.

На `ProductTypes` рядом с актуальной CPA добавляется фактический ROAS по категории. Он считается как суммарная ценность конверсий категории, делённая на суммарные рекламные расходы категории за тот же период. Рядом должен быть виден рассчитанный Target ROAS.

Если фактический ROAS выше Target ROAS, ячейка фактического ROAS подсвечивается зелёным; если ниже — нежно-красным. Target ROAS в этой формуле означает безубыточность, без заложенной дополнительной прибыли после рекламы.

Порядок колонок ProductTypes: галочка включения, уровни product type, benchmark label, priority label, winter, spring, summer, autumn, затем Target CPA и Target ROAS. Target CPA переносится из конца листа. Комментарий должен оставаться последней колонкой.

Уточнение: Target ROAS является ручным полем и должен быть жёлтым. Ручной Target ROAS сохраняется за категорией и имеет приоритет; без ручного значения действует расчёт через маржу.

Порядок Settings: основные настройки (Merchant ID, названия листов, общий Target CPA и маржа), фильтры фидов вторым блоком, включение функций, сезонность, категории товаров, этапы воронки, карантин с подпунктами, служебные настройки последними. Benchmark label field по умолчанию — product_type_l1. Служебные настройки оставляем как есть, самым нижним блоком.

Дата выхода из карантина: вводим одну общую дату по товару для всех карантинов. Неважно, какой был карантин: записываем последнюю дату, когда товар вышел из карантина и снова стал активным в отношении карантина. Храним её в ProductDiagnostics, без дополнительного служебного листа. При проверке используем период из Settings, но не учитываем данные до этой даты. Период постепенно вырастает до обычного окна, затем снова становится скользящим.
