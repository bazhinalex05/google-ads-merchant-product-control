# Unified Merchant Product Control - структурированная ожидаемая логика

Статус: организованная версия пользовательской диктовки. Это не техническое описание текущего кода и не финальная документация.

Источник: [ожидания пользователя](expected-user.md). Фактическая реализация описана в [технической документации](../technical-reference.md).

## 1. Назначение скрипта

Скрипт нужен для ecommerce-проектов, где товары из Merchant Center нужно:

- собрать в рабочую Google Sheets таблицу;
- разложить по категориям и рабочим группам;
- определить funnel stage каждого товара;
- временно выключать проблемные товары через карантин;
- сформировать первый лист `Products` как дополнительный фид для Merchant.

Главная цель: управлять показами товаров через `excluded_destination`, funnel stage и priority group.

## 2. Обязательные условия

### Products всегда первый

Лист `Products` является дополнительным фидом для Merchant и всегда должен быть первым листом таблицы.

На листе `Products` всегда должны быть товары. Если в Merchant настроено автообновление допфида, Merchant может в любой момент забрать первый лист. Если в этот момент `Products` пустой, ломается вся цепочка, которая настроена через таблицу.

### Формулы и скрипт

Если часть логики можно стабильно сделать формулами в таблице, чтобы не нагружать Google Ads Script и не доводить запуск до timeout, эту часть можно делать формулами.

Если таблица начинает ломаться или уходить в timeout из-за перегруза формулами, эту часть нужно переносить в скрипт.

### Резиновые ручные листы

Листы `ProductTypes` и `Seasonality` должны быть резиновыми.

Они должны учитывать, что у клиента может меняться:

- структура сайта;
- структура каталога;
- количество категорий;
- количество подкатегорий;
- количество товаров.

Ручные галочки должны быть привязаны к конкретной категории или конкретному ID товара. Галочки не должны съезжать на случайные строки после перестроения листов.

### Boolean-поля как флажки

Все boolean-поля, которые отображаются в таблице как флажки, должны быть именно checkbox-ячейками.

То, что нажимается руками, и вообще все флажки в таблице должны оставаться флажками.

Текстовых значений `TRUE` или `FALSE` в таблице быть не должно ни при каких обстоятельствах.

### Settings

На листе `Settings` настройки должны быть разбиты на логические блоки, чтобы листом было удобно пользоваться.

Обязательные поля и поля, которые нужны при каждой новой настройке проекта, должны подсвечиваться красным в ячейке с названием настройки.

Ячейки со значениями, которые заполняются вручную, должны подсвечиваться жёлтым.

Все комментарии в таблице должны быть только на украинском языке.

### Ручные ячейки

На листах `Settings`, `ProductTypes` и `Seasonality` ручные ячейки должны быть визуально отделены жёлтой заливкой.

К ручным ячейкам относятся:

- ячейки с галочками;
- ячейки с комментариями;
- ячейки, где клиент должен что-то написать вручную.

## 3. Источники данных

Скрипт должен получать данные из API и из рабочей Google Sheets таблицы.

### Merchant Center

Из Merchant Center по каждому товару нужны:

- ID товара;
- product type или другая цепочка категории;
- цена товара;
- feed/data source;
- feed label;
- content language;
- benchmark label, если он хранится в Merchant;
- priority label, если он хранится в Merchant или должен быть передан туда.

### Google Ads

Из Google Ads по каждому товару нужны:

- клики;
- показы;
- расходы;
- конверсии;
- ценность конверсий;
- средний CPC для проверки дорогого клика.

Периоды могут быть разными:

- отдельный период для funnel stage;
- отдельный период для карантина `клики без продаж`;
- отдельный период для карантина `перетраты относительно цены`;
- только вчерашний день для карантина `дорогой клик`.

### Google Sheets

Из таблицы скрипт должен читать ручные настройки и ручной выбор клиента:

- настройки на листе `Settings`;
- выбранные категории и сезонность на `ProductTypes`;
- потоварную сезонность;
- историю карантина, если она уже есть.

## 4. Ограничение по фидам

У клиента может быть несколько фидов.

В настройках должна быть возможность указать один или несколько feed/data source ID через запятую.

Скрипт должен работать только с выбранными фидами:

- анализировать товары только из указанных фидов;
- не включать товары из остальных фидов в расчёты;
- по возможности не тратить время API на ненужные фиды.

## 5. Категории и product type

Скрипт должен знать, где лежит каждый товар в каталоге клиента.

Возможные источники цепочки категорий:

1. Стандартный `product_type`, который уже передаётся сайтом в Merchant.
2. Итоговый `product_type` в Merchant после обработки дополнительным фидом.
3. Другое поле, например custom label, нестандартный атрибут или отдельный внешний источник.

Если правильная цепочка уже попала в Merchant через дополнительный фид, скрипт должен читать итоговые данные из Merchant, а не исходный фид сайта.

Если правильная цепочка лежит в custom label, например `custom_label_2`, скрипт должен уметь использовать это поле как источник product type.

## 6. ProductTypes

Лист `ProductTypes` нужен для дерева категорий.

На листе должны быть:

- уровни product type;
- галочка включения категории;
- сезонные галочки по категориям;
- поля для benchmark/priority, если они назначаются на уровне категории;
- актуальная CPA категории;
- ручной `target_cpa` категории;
- служебные поля только если они реально нужны для стабильной работы.

На старте проекта все категории должны быть включены по умолчанию.

Выбор клиента должен сохраняться между запусками. Если дерево перестроилось из-за новых категорий или подкатегорий, галочки должны оставаться привязанными к категориям, а не к случайным строкам.

### Наследование выбора категорий

Любая отмеченная категория на любом уровне становится выбранной веткой, даже если её родительская категория выше по дереву не отмечена.

Если категория верхнего уровня не выбрана, а внутри во вложенности стоят галочки на категориях второго уровня или ниже, эти вложенные галочки должны работать.

Если ниже в выбранной ветке нет более точных отмеченных категорий, включается всё поддерево этой ветки.

Если внутри выбранной ветки есть более точный выбор, показываются:

- отмеченная родительская категория и товары, которые лежат прямо в ней;
- отмеченные подкатегории;
- товары внутри отмеченных подкатегорий.

Неотмеченные соседние ветки внутри этой части дерева должны получать `excluded_destination`.

### Подсветка actual CPA относительно target CPA

На листе `ProductTypes` скрипт должен сравнивать актуальную CPA категории с ручным `target_cpa`.

Если актуальная CPA выше `target_cpa`, ячейка актуальной CPA должна подсвечиваться самым светлым красным цветом.

Если актуальная CPA ниже `target_cpa`, ячейка актуальной CPA должна подсвечиваться зелёным.

## 7. Funnel Stage

Скрипт должен присвоить каждому товару funnel stage.

Расчёт строится по кликам, показам и конверсиям за выбранный период funnel stage.

Логика:

- товары с продажами попадают в `1 продажі`;
- товары без показов попадают в `6 без стат`;
- для остальных товаров скрипт делит ассортимент или benchmark-группу на верхнюю и нижнюю часть по кликам;
- отдельно делит на верхнюю и нижнюю часть по показам;
- комбинация высоких/низких кликов и высоких/низких показов формирует этапы 2-5.

Нужны отдельные сегменты:

- высокие клики;
- низкие клики;
- высокие показы;
- низкие показы.

## 8. Benchmark и Priority

Benchmark label и priority label должны быть разными сущностями.

### Benchmark label

Benchmark label нужен для расчёта.

Он определяет группу сравнения, внутри которой скрипт считает клики, показы и funnel stage.

Товары из других benchmark-групп не должны участвовать в расчёте этой группы.

Товары без benchmark должны попадать в benchmark-группу `other`, которая считается отдельно.

Benchmark должен быть видимым по каждому товару в диагностике или отдельном рабочем листе.

Benchmark не нужно передавать обратно в Merchant как отдельный custom label.

### Priority label

Priority label нужен для управления бюджетом и структурой продвижения.

Он должен передаваться в Merchant, чтобы в Google Ads можно было создавать группы товаров по priority.

У priority тоже должна быть группа `other` для товаров без заданного приоритета.

В настройках должны быть две разные настройки:

- из какого поля читать benchmark label для расчёта;
- в какое поле писать priority label для передачи в Merchant.

Одна общая настройка для benchmark и priority недостаточна.

### Лист клиентских приоритетов

В таблице должен быть отдельный лист `Priorities` для ручного списка приоритетных товаров от клиента.

Назначение листа: принимать клиентские списки конкретных товаров, которым нужно назначить priority group, без создания отдельного внешнего допфида.

На старте лист должен быть пустым.

Минимальная структура листа:

- `id`;
- `priority_group`.

Лист должен поддерживать сценарий, когда клиент передаёт таблицу с ID товаров и группой приоритета. Эти данные вручную вставляются в лист клиентских приоритетов.

Скрипт должен:

- читать `id` и `priority_group` с этого листа;
- по ID товара присваивать товару указанную priority group;
- показывать priority group в `ProductDiagnostics`;
- выводить priority group на `Products`;
- передавать priority group в Merchant через допфид `Products`.

Этот лист не должен обновляться, стираться или перезаписываться скриптом. Он должен хранить вручную внесённые приоритеты клиента.

## 9. Карантин

Карантин временно выключает товары через `excluded_destination`.

Должно быть три правила карантина.

У каждого правила должны быть свои:

- включатель;
- период проверки;
- порог;
- срок паузы.

### Клики без продаж

Если за выбранный период у товара было достаточно кликов, но не было продаж, товар ставится на паузу.

Период и порог кликов задаются в настройках.

### Перетраты относительно цены

Если товар потратил слишком много относительно своей цены и не дал достаточной отдачи, товар ставится на паузу.

Период проверки задаётся отдельно.

Порог задаётся в процентах относительно цены товара.

### Продажи с дорогим CPA

Нужен отдельный карантин для товаров, у которых есть продажи, но текущий CPA слишком высокий относительно категорийного `target_cpa`.

Источник `target_cpa`: ручное значение на листе `ProductTypes` для категории товара.

Если товар находится в категории, где задан `target_cpa`, и текущий CPA товара превышает этот `target_cpa` с учётом настроенного порога превышения, товар должен ставиться на паузу через `excluded_destination`.

У правила должны быть отдельные настройки:

- включатель правила;
- период проверки в днях;
- срок паузы в днях;
- порог превышения `target_cpa`.

В диагностике или данных Dashboard должны быть видны:

- spend товара за период проверки;
- текущий CPA товара за период проверки;
- `target_cpa` категории;
- величина превышения текущего CPA над `target_cpa`.

### Дорогой клик

Дорогой клик проверяется только за вчерашний день.

Причина: доступен средний CPC, а не данные по каждому отдельному клику.

Порог дорогого клика задаётся вручную.

## 10. Листы карантина

Названия листов не принципиальны. Нужны две роли.

### Текущий карантин

Лист текущего карантина должен показывать:

- какие товары сейчас на паузе;
- по какой причине;
- когда они выйдут из карантина.

На этом листе не должно быть товаров, которые уже не находятся в активном карантине.

### История карантина

Исторический лист должен хранить:

- ID товара;
- счётчик, сколько раз товар попадал в карантин.

История нужна, чтобы видеть товары, которые регулярно становятся проблемными, и переносить старые счётчики после переустановки скрипта.

Даты и подробные причины на историческом листе не обязательны.

Исторический лист не должен расти бесконечно. Ориентир лимита: не больше 1000 строк.

## 11. Products

Первый лист `Products` должен быть чистым дополнительным фидом для Merchant.

На листе должны быть:

- `id`;
- два поля `excluded_destination`;
- custom label для funnel stage;
- custom label для priority group.

ID и `excluded_destination` может писать скрипт.

Funnel stage и priority group можно подтягивать формулами, если это экономит время и не ломает стабильность.

Benchmark label на `Products` передавать не нужно.

Запись на `Products` можно разделять на шаги, чтобы снизить риск timeout.

## 12. ProductDiagnostics

`ProductDiagnostics` должен быть листом объяснения решений скрипта.

По каждому товару должны быть видны:

- ID;
- title;
- `excluded_destination`;
- data source ID;
- feed label;
- content language;
- product type full path;
- product type all paths;
- клики, показы и конверсии для funnel stage;
- funnel stage;
- click segment;
- impression segment;
- benchmark label;
- priority label;
- пороги кликов и показов внутри benchmark;
- данные для карантина `клики без продаж`;
- данные для карантина `перетраты относительно цены`;
- данные для карантина `дорогой клик`;
- причина исключения товара;
- атрибутированные конверсии и ценность конверсий по прошлому funnel stage.

Не должно быть бесполезных колонок.

Поля `product_type_source` и `product_type_status` требуют проверки: пользователь не понимает их ценность.

Период funnel stage можно не писать отдельной колонкой, если он понятен из настроек.

## 13. Сезонность

Сезонность должна работать по категориям и по товарам.

Если сезонность нигде не размечена, все товары считаются включёнными.

Пустые сезонные галочки не должны выключать товары.

Если сезонность задана только в одной категории, она применяется только к этой категории.

Если текущий сезон не совпадает с отмеченным сезоном товара или категории, товар получает `excluded_destination`.

Сезонные галочки должны сохраняться за категориями при обновлении скрипта, даже если дерево категорий расширилось.

### Потоварная сезонность

Если у товара задана потоварная сезонность, она главнее категорийной.

Если у товара нет потоварных сезонных галочек, это не должно автоматически выключать товар.

Товар без потоварных сезонных галочек работает по категорийной сезонности, а если сезонность нигде не задана, считается включённым.

## 14. Dashboard и DashboardData

`Dashboard` и `DashboardData` пока не описываются.

По ним нужно принять отдельное решение позже.

## 15. Общий Target CPA и ROAS по марже на ProductTypes

### 15.1. Общий и категорийный Target CPA

- Предусмотреть общий Target CPA для всего сайта.
- Сохранить ручной Target CPA для каждой категории на `ProductTypes`.
- Если у категории задан ручной Target CPA, применять его; иначе использовать общий Target CPA сайта.
- Сохранить сравнение фактической CPA с применяемым Target CPA и соответствующую подсветку.

### 15.2. Общая и категорийная маржа

- Предусмотреть общую процентную маржу для сайта.
- Дать возможность вручную указать отдельную маржу категории на `ProductTypes`.
- Если маржа категории задана, использовать её; иначе использовать общую маржу сайта.
- Маржа для расчёта означает долю выручки после остальных учитываемых затрат, но до рекламы. Она не равна наценке на закупочную цену.

### 15.3. Расчёт Target ROAS

Target ROAS на ProductTypes — жёлтая ручная ячейка. Заданный вручную порог категории сохраняется между прогонами и имеет приоритет над расчётом. Если ручной порог отсутствует, используется формула по марже.

Target ROAS безубыточности = 1 / маржа в долях.

Результат отображается в процентах: маржа 30% даёт ROAS 3,333..., или 333,33%.

При общей одинаковой процентной марже порог ROAS для всех категорий одинаков. Средний чек не изменяет этот порог: допустимая CPA безубыточности равна среднему чеку, умноженному на маржу, поэтому отношение среднего чека к такой CPA равно 1 / маржа. Эта связь объясняет расчёт и не заменяет ручной Target CPA.

Порог соответствует безубыточности по учтённым затратам и не содержит дополнительной целевой прибыли после рекламы.

### 15.4. Фактический ROAS и отображение

Порядок колонок: включение, уровни product type, benchmark label, priority label, четыре сезона, Target CPA, Target ROAS. Комментарий находится в последней колонке. Существующие ручные Target CPA сохраняются при переносе.

- На `ProductTypes` добавить фактический ROAS рядом с актуальной CPA и показывать рассчитанный Target ROAS категории.
- Фактический ROAS = сумма ценности конверсий категории / сумма рекламных расходов категории за один и тот же период. Не использовать среднее арифметическое ROAS отдельных товаров.
- При каждом прогоне сравнивать фактический ROAS с рассчитанным Target ROAS категории.
- Выше Target ROAS: зелёная заливка ячейки фактического ROAS.
- Ниже Target ROAS: нежно-красная заливка ячейки фактического ROAS.

Карантин с подпунктами; 8. Служебные настройки. Служебный блок остаётся последним, его содержимое не меняется. Значение benchmark_label_field по умолчанию: product_type_l1; существующий выбор пользователя сохраняется.

- Гарантирует ли скрипт, что `Products` всегда остаётся первым листом?
- Может ли `Products` стать пустым во время автообновления Merchant или во время частичного сбоя?
- Какие части сейчас сделаны формулами, а какие скриптом, и где есть риск timeout?
- Все ли ручные ячейки на `Settings`, `ProductTypes` и `Seasonality` подсвечены жёлтым?
- Подсвечены ли обязательные настройки красным в ячейке с названием настройки?
- Работает ли ограничение по feed/data source ID на уровне API или только после получения всех товаров?
- Корректно ли скрипт читает product type из всех нужных источников?
- Сохраняются ли галочки ProductTypes по категориям, а не по строкам?
- Совпадает ли текущая логика наследования категорий с ожидаемой?
- Разделены ли benchmark и priority в коде?
- Записывается ли в Products priority, а не benchmark?
- Есть ли в ProductDiagnostics все данные для объяснения funnel stage и карантина?
- Разделены ли текущий карантин и исторический карантин так, как ожидается?
- Не растёт ли история карантина бесконечно?
- Совпадает ли текущая логика сезонности с ожидаемой, особенно приоритет потоварной сезонности над категорийной?

## Общая дата выхода из карантина

- В ProductDiagnostics хранится last_quarantine_exit_date по ID товара, одна для всех правил карантина, без отдельного служебного листа.
- Дата обновляется при переходе из карантина в состояние без активного карантина. Завершение одного правила при продолжающемся другом не считается выходом.
- Начало проверки каждого правила: более поздняя из даты выхода и начала обычного периода этого правила. Конец периода и исключение последних дней сохраняют свои настройки; дорогой клик проверяется строго за вчера.
- Если начало позже конца, данных для проверки пока нет. По мере времени период вырастает до заданной продолжительности, затем скользит обычным образом.
- Ограничение относится только к карантину, не к статистике воронки. Дата сохраняется между запусками и не обновляется ежедневно без нового выхода.
