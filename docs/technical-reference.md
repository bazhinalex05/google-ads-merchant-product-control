# Unified Merchant Product Control - актуальная фактическая логика листов из кода

Статус: актуальный технический документ по фактической работе текущего кода.

Источник: `google-ads-merchant-product-control/script.js`.

Сверка выполнена 8 сентября 2026 по текущему `script.js`, изменениям относительно предыдущей версии документа и локальным регрессионным сценариям. Это описание реализации, а не заявление о прохождении всех сценариев в Google Ads. Проверка фактического выхода из карантина на живом проекте остаётся отложенной. При этой актуализации сам скрипт не изменялся.

Документ описывает факт из кода: какие листы создаются, какие колонки пишутся, откуда берутся значения и что скрипт перезаписывает.

## Порядок основных листов

В начале и в конце полного запуска код вызывает `ensureCoreSheetOrder_`.

Первые три листа принудительно ставятся в таком порядке:

1. `Products`;
2. `Dashboard`;
3. `DashboardData`.

Остальные листы создаются или используются по именам из объекта настроек, но их позиция после первых трёх отдельно не фиксируется. Не каждое имя вынесено в ячейку Settings: пользовательские настройки имён есть у Dashboard, DashboardData и Priorities.

## 1. Products

### Роль листа

`Products` - выходной лист допфида Merchant Center.

Код пишет на этот лист:

- ID товара;
- два `excluded_destination`;
- custom label для funnel stage;
- custom label для priority group, если он включён настройкой.

### Где формируется

Рабочая строка товара формируется в `buildProductsOutputRows_`.

Финальный компактный допфид записывается в `writeProductsSheet_`.

### Колонки

#### A: `id`

Источник: Merchant API.

Как попадает:

- `getMerchantProducts_` читает товары Merchant API;
- у товара берётся `offerId`;
- в рабочей строке он хранится как `p.offerId`;
- `writeProductsSheet_` пишет его в колонку A.

Назначение: ID товара для матчинга допфида с товаром Merchant Center.

#### B: `excluded_destination`

Источник: расчёт скрипта.

Если товар должен быть выключен, пишется значение настройки `shopping_excluded_value`.

Если причин выключения нет, ячейка пустая.

Причины, которые могут заполнить колонку:

- `PRODUCT_TYPE_NOT_ALLOWED` - категория не разрешена через `ProductTypes`;
- `SEASONALITY` - товар не подходит под активный сезон;
- причины активного карантина: `NO_SALES`, `SPEND_OVER_MARGIN`, `EXPENSIVE_CLICK`, `TARGET_CPA`.

#### C: `excluded_destination`

Источник: расчёт скрипта.

Логика такая же, как у колонки B.

Если товар должен быть выключен, пишется значение настройки `display_excluded_value`.

Если причин выключения нет, ячейка пустая.

#### D: custom label для funnel stage

Заголовок берётся из настройки `funnel_stage_output_attribute`.

Источник значения: расчёт Funnel Builder.

Как попадает:

- Google Ads статистика за период `funnel_days_ago` попадает в `funnelStatsMap`;
- `calculateFunnelRows_` считает сегмент кликов, сегмент показов и итоговый `funnelStage`;
- `buildProductsOutputRows_` кладёт stage в рабочую строку;
- `writeProductsSheet_` пишет значение в колонку D.

Типовые значения:

- `1 продажі`;
- `2 вк+вп`;
- `3 вк+нп`;
- `4 нк+вп`;
- `5 нк+нп`;
- `6 без стат`.

#### E: custom label для priority group

Колонка появляется только если `priority_output_attribute` заполнен и является допустимым `custom_label_0...custom_label_4`.

Заголовок берётся из настройки `priority_output_attribute`.

Источник значения: `priorityLabel`, который выбирается в `choosePriorityLabel_`.

Порядок источников:

1. лист `Priorities` по точному ID товара;
2. категорийный `priority_label` с листа `ProductTypes`;
3. значение из Merchant API по настройке `priority_label_field`;
4. fallback `other`.

Если один и тот же товар есть на `Priorities`, а его категория имеет `priority_label` на `ProductTypes`, в `Products` попадёт значение с `Priorities`.

### Очистка и запись

Если `rows` пустой или не передан, `writeProductsSheet_` ничего не пишет и не чистит. Старое содержимое `Products` сохраняется.

Если строки есть:

- код переписывает заголовки;
- пишет строки данных чанками через `writeRowsInChunks_`;
- очищает только хвост ниже записанных строк в управляемой ширине;
- при включённом `enableManagedSheetFormatting` применяет форматирование.

`Products` не заполняется формулами. Все значения записываются скриптом. Этот способ подтверждён пользователем: переход на формулы не планируется.

Запись не является одной атомарной заменой листа: сначала заголовки и новые блоки, затем очистка хвоста. При прерывании возможна смесь старых и новых строк; это не механизм автоматического отката. В наблюдавшемся обычном прогоне опустошения листа не было, но наблюдение не доказывает отсутствие краткого промежуточного состояния между проверками.

## 2. Dashboard

### Роль листа

`Dashboard` - визуальный лист отчёта.

### Где формируется

Лист создаётся или обновляется через `ensureDashboardSheet_`.

Если лист пустой или распознан как сгенерированный скриптом, вызывается `writeInitialDashboardSheet_`.

Если лист содержит ручной/кастомный layout и не распознан как сгенерированный, код логирует, что ручной layout сохранён.

### Что пишет код

Код заполняет блоки формулами, которые смотрят в `ProductDiagnostics`, `DashboardData`, `Seasonality` и `Settings`.

Основные блоки:

- товары с конверсиями;
- кликабельные товары;
- популярные в поиске;
- расходы по этапам;
- общая карточка ROAS/CPA/Conversions/CValue/Spend;
- карточка карантина;
- карточка сезонности.

### Карантинная карточка

Сейчас карточка карантина считает:

- всего активных;
- `NO_SALES`;
- `SPEND_OVER_MARGIN`;
- `EXPENSIVE_CLICK`;
- `TARGET_CPA`.

Статусы правил берутся формулами из `Settings`.

Количество товаров считается по `ProductDiagnostics`, колонка `exclusion_reasons`.

## 3. DashboardData

### Роль листа

`DashboardData` - служебный лист с агрегированными данными для Dashboard.

### Где формируется

Лист пишет `writeDashboardDataSheet_`.

### Очистка и запись

Если лист пустой, код вызывает `sheet.clear()` и разбивает объединения.

Если лист уже существовал, код очищает содержимое в текущей используемой области.

После этого код заново пишет блоки данных.

### Блоки данных

Код пишет:

- периоды данных;
- общую сводку за 14 и 30 дней;
- долю расходов по группам;
- расходы по группам и этапам;
- funnel-блоки по группам.

Группы строятся из строк `ProductDiagnostics` / `outputRows`.

## 4. Priorities

### Роль листа

`Priorities` - ручной лист для списка приоритетных товаров от клиента.

### Где создаётся

Лист создаётся функцией `getOrCreatePrioritiesSheet_`.

Имя листа берётся из настройки `priority_sheet_name`.

Дефолтное имя: `Priorities`.

Если в старой тестовой таблице есть лист `ClientPriority`, а `Priorities` ещё нет, код переименует `ClientPriority` в `Priorities`.

### Колонки

#### A: `id`

Источник: ручной ввод или вставка списка клиента.

Скрипт создаёт заголовок, но не заполняет значения.

При чтении значение нормализуется через `normOfferId_`.

#### B: `priority_group`

Источник: ручной ввод или вставка списка клиента.

Скрипт создаёт заголовок, но не заполняет значения.

При чтении значение сохраняется в карту `priorityMap`.

#### C: `comment`

Источник: ручной комментарий. Создаётся генератором вместе с `id` и `priority_group`; не участвует в выборе приоритета и не передаётся в Products. Значения не очищаются и не перезаписываются.

### Очистка и запись

`ensurePrioritiesSheet_` создаёт заголовки, если их нет.

Скрипт не очищает строки данных и не перезаписывает список клиента.

При включённом форматировании:

- заголовки A:B и `comment` получают синий фон;
- ручные области A:B и `comment` ниже заголовка подсвечиваются жёлтым;
- первая строка замораживается.

### Как влияет на Products и ProductDiagnostics

`readPrioritiesMap_` читает пары `id -> priority_group`.

Если ID товара есть на `Priorities`, это значение становится `priorityLabel` товара.

Это значение попадает:

- в `ProductDiagnostics`, колонка `priority_label`;
- в `Products`, колонка E, если включён `priority_output_attribute`.

Значение с `Priorities` сильнее категорийного priority с `ProductTypes` и сильнее priority из Merchant API.

## 5. ProductTypes

### Роль листа

`ProductTypes` - дерево категорий и ручные настройки по категориям.

Код использует его для:

- фильтрации категорий;
- категорийного benchmark label;
- категорийного priority label;
- категорийной сезонности;
- target CPA по категории;
- подсветки actual CPA относительно target CPA.

### Когда строится

Лист строится, если включено хотя бы одно:

- `enable_product_type_filter`;
- `enable_seasonality_filter`;
- `enable_target_cpa_rule`.

### Источник дерева категорий

Базовый источник товаров: Merchant API.

Product type у товара может прийти:

- из custom label, если включён `enable_product_type_custom_label_source`;
- из штатного `productTypes` / `productType` Merchant API;
- из custom attributes с именами `product_type`, `product type`, `producttypes`;
- из внешнего XML `product_type_feed_url`, если он указан.

Если указан `product_type_feed_url`, код строит карту `id -> product_type` и подменяет product type у товара.

Если полного совпадения ID во внешнем XML нет, `product_type_id_prefixes_to_strip` и `product_type_id_suffixes_to_strip` позволяют пробовать ID Merchant без заданного начала/окончания. ID во внешнем XML не обрезаются; ID в Products и ключи статистики не заменяются. Подробный порядок сопоставления приведён в разделе 22.

### Сохранение ручных значений

Перед пересборкой `readProductTypeManualStateMap_` читает существующий лист.

Состояние сохраняется по `path_key`, который строится из `product_type_l1...product_type_lN`.

Сохраняются:

- `Вмикаємо`;
- benchmark label;
- `priority_label`;
- `winter`;
- `spring`;
- `summer`;
- `autumn`;
- `target_cpa`;
- `margin_percent`;
- числовой ручной `target_roas` (не вычисленное значение формулы);
- `comment`.

Если категория новая, `Вмикаємо` по умолчанию `TRUE`, остальные ручные поля пустые или `FALSE`.

### Колонки

#### A: `Вмикаємо`

Источник: сохранённое ручное значение.

Если значения нет, код ставит `TRUE`.

Формат: checkbox validation.

Используется для фильтра категорий при `enable_product_type_filter=TRUE`.

#### `product_type_l1...product_type_lN`

Источник: product type товаров после выбора источника категории.

Количество уровней зафиксировано в коде: пять. Настройка `max_product_type_levels` удалена из генератора и чтения Settings.

Строка дерева выводится разреженно: значение пишется только на уровне текущей категории.

#### `benchmark_label`

Источник: ручное значение на `ProductTypes`.

Код не рассчитывает его автоматически.

Используется как категорийное benchmark-правило.

Для товара выбирается самое глубокое совпадающее правило.

Значение попадает в `ProductDiagnostics` как `product_type_benchmark_label`.

#### `priority_label`

Источник: ручное значение на `ProductTypes`.

Код не рассчитывает его автоматически.

Используется как категорийный источник `priorityLabel`, если для товара нет значения на `Priorities`.

Для товара выбирается самое глубокое совпадающее правило.

Значение попадает в `ProductDiagnostics` и в `Products` через `priorityLabel`.

#### `winter`, `spring`, `summer`, `autumn`

Источник: ручные checkbox-значения на `ProductTypes`.

Используются для категорийной сезонности.

Если на строке категории включён хотя бы один сезон, строка становится сезонным правилом.

Для товара выбирается самое глубокое совпадающее сезонное правило.

#### `path_key`

Источник: расчёт скрипта из полного пути категории.

Назначение: технический ключ для сохранения ручных значений при пересборке.

После форматирования колонка скрывается.

#### `path_depth`

Источник: расчёт глубины пути категории.

После форматирования колонка скрывается.

#### `has_season_rule`

Источник: формула, которую пишет скрипт.

Показывает, есть ли в строке хотя бы одна сезонная галочка.

После форматирования колонка скрывается.

#### `aov`

Источник: цены товаров из Merchant, сгруппированные по product type. Несмотря на имя `aov`, это не `conversion_value / conversions`: конечная категория использует среднюю положительную цену, родитель усредняет дочерние AOV и собственную конечную группу.

#### `conversions_30d`

Источник: Google Ads статистика за 30 дней.

#### `spend_30d`

Источник: Google Ads статистика за 30 дней.

#### `actual_cpa_30d`

Источник: расчёт скрипта.

Формула: `spend_30d / conversions_30d`, если конверсии больше нуля.

Подсветка использует положительный `target_cpa` строки, иначе `default_target_cpa` из Settings. При положительном actual CPA превышение эффективной цели даёт светло-красный фон, значение не выше цели даёт зелёный фон. Без положительного actual CPA или эффективной цели фон белый. Допуск карантина 20% здесь не применяется.

#### `conversion_value_30d`

Источник: Google Ads статистика за 30 дней.

#### `target_cpa`

Источник: ручное значение на `ProductTypes`.

Используется для:

- подсветки `actual_cpa_30d`;
- карантина `TARGET_CPA`.

Для товара выбирается target CPA по самому глубокому совпадающему пути категории.

#### `target_roas`

Ручное положительное число либо формула безубыточного ROAS по марже. Формат обычный процентный: значение 3 означает 300%. Формула при отсутствии ручного значения: `100 / effectiveMarginPercent`, где маржа 30 означает 30%.

#### `margin_percent`

Ручная маржа категории до рекламы. Пустая ячейка использует общую `default_margin_percent`, но общая маржа не копируется в ячейку. Здесь число 30 означает 30%, в отличие от хранения ROAS коэффициентом.

#### `actual_roas_30d`

Отношение ценности конверсий к расходам категории за обычные 30 дней. При отсутствии расходов ячейка пустая. Расчёт и подсветка подробно описаны в разделе 14.

#### `comment`

Источник: ручное значение на `ProductTypes`.

Скрипт сохраняет его по `path_key`.

### Логика галочек категорий

`buildAllowanceRulesFromRows_` собирает все строки, где `Вмикаємо=TRUE`.

Для отмеченной категории код определяет, есть ли под ней отмеченные дочерние категории.

Если отмечена категория и под ней нет более точных отмеченных категорий, разрешается всё её поддерево.

Если отмечена категория и внутри неё есть отмеченные дочерние категории, разрешаются:

- товары прямо в отмеченной категории;
- отмеченные дочерние ветки;
- поддеревья отмеченных дочерних веток, если под ними нет более точного выбора.

Неотмеченные соседние ветки внутри этой части дерева не разрешаются.

Если верхний уровень не отмечен, но отмечена категория второго или третьего уровня, эта нижняя галочка работает сама по себе.

## 6. Seasonality

### Роль листа

`Seasonality` - потоварная сезонность и итоговый сезонный статус товара.

### Где формируется

Лист пишет `writeSeasonalitySheet_`.

Перед записью `readSeasonalityManualStateMap_` читает ручные значения старого листа по ID товара.

### Колонки

#### A: `id`

Источник: `outputRows`, то есть товары, собранные из Merchant API и обработанные скриптом.

#### B: `title`

Источник: Merchant API.

#### C: `product_type_full_path`

Источник: рабочая строка товара, сформированная из product type.

#### `product_type_l1...product_type_lN`

Источник: разложенный product type товара.

Количество уровней фиксировано: пять.

#### `manual_winter`, `manual_spring`, `manual_summer`, `manual_autumn`

Источник: ручные значения старого `Seasonality`, сохранённые по ID товара.

Если старого значения нет, код ставит `FALSE`.

Формат: checkbox validation.

Эти колонки видимые и подсвечены жёлтым.

#### `category_winter`, `category_spring`, `category_summer`, `category_autumn`

Источник: формулы, которые смотрят категорийные сезонные правила на `ProductTypes`.

После форматирования эти колонки скрываются.

#### `winter`, `spring`, `summer`, `autumn`

Источник: формулы итоговой сезонности.

Логика:

- если у товара включена хотя бы одна ручная сезонная галочка, итог берётся только из ручных потоварных галочек;
- если ручных потоварных галочек нет, итог берётся из категорийной сезонности.

После форматирования эти колонки скрываются.

#### `comment`

Источник: ручной комментарий старого `Seasonality`, сохранённый по ID товара.

Ячейки комментариев подсвечены жёлтым.

### Как влияет на Products

Если `enable_seasonality_filter=FALSE`, сезонность не исключает товары.

Если `enable_seasonality_filter=TRUE`, код вычисляет эффективные сезоны по ручным данным Seasonality и категорийным правилам ProductTypes. Для решения в текущем запуске используются карты в памяти; формулы итоговых колонок листа отображают сезонность, но скрипт не ждёт их нового результата для исключения.

Если у товара нет ни потоварной, ни категорийной сезонности, товар считается разрешённым.

Если у товара есть сезонность, но ни один активный сезон из Settings не совпадает, товар получает `SEASONALITY` и `excluded_destination` на `Products`.

## 7. ProductDiagnostics

### Роль листа

`ProductDiagnostics` - диагностический лист по каждому товару.

Он показывает исходные данные, расчётные значения, причины исключения, карантинные метрики, benchmark/priority и attribution-поля.

### Где формируется

Лист пишет `writeProductDiagnosticsSheet_`.

Строки берутся из тех же `outputRows`, из которых строится `Products`.

### Очистка и запись

Если `product_diagnostics_start_row <= 1`, код очищает содержимое листа, пишет заголовок и все строки.

Если `product_diagnostics_start_row > 1`, код не чистит весь лист и записывает с указанной позиции в текущем массиве данных. Это не возобновление прерванного запуска: расчёты выполняются снова. ID, флаг карантина и дата выхода отдельно обновляются для всех текущих товаров; подробности в разделе 19.

### Колонки и источники

#### `id`

## 10. Settings

### Роль листа

`Settings` хранит настройки запуска.

### Чтение и пересборка

`readSettings_` читает колонку A как ключ, колонку B как значение.

После чтения текущих значений код вызывает `writeSettingsTemplate_`, поэтому шаблон Settings пересобирается при каждом запуске.

Перед записью шаблона код:

- очищает data validations на всём листе;
- вызывает `sheet.clear()`;
- снова очищает data validations;
- записывает актуальный шаблон настроек.

Старые значения сохраняются только для известных ключей, которые код успел прочитать до пересборки.

### Порядок блоков Settings

Генератор выставляет следующий порядок независимо от ручной перестановки строк:
1. Основные настройки: Merchant ID, общий Target CPA, общая маржа.
2. Фильтры фидов и Merchant API.
3. Основные включатели функций.
4. Этапы воронки, benchmark и priority.
5. Активные сезоны.
6. Категории: custom label, внешний XML, префиксы и постфиксы.
7. Карантин: выходные значения, общие параметры, четыре правила.
8. Служебные настройки.

Три переключателя диагностики/дашбордов и три имени листов перенесены в последний блок. Это изменение расположения, а не выключение функций. Значения и процентные форматы определяются по ключу колонки A, не по номеру строки.

### Основные настройки листов

#### `merchant_id`

Источник: ручное значение.

Используется для чтения Merchant API.

#### `default_target_cpa`

Общая цель CPA сайта в валюте Ads. Дефолт 0 означает отсутствие положительной цели. Используется при подготовке эффективного Target CPA каждой строки ProductTypes и для подсветки actual CPA при отсутствии положительной ручной цели.

#### `default_margin_percent`

Общая маржа до рекламы в процентных пунктах: 30 означает 30%. Дефолт 0. Используется для формулы Target ROAS при пустой марже строки; не является порогом карантина расходов относительно цены.

Тип: number, дефолт 0. Это общая цель, а не заполнение всей колонки ProductTypes. Положительный ручной Target CPA строки имеет приоритет, иначе в памяти используется общая цель. Применение к товару проходит через выбор категорийного правила; особенности дочерних категорий описаны в разделе 14.

### `default_margin_percent`

Тип: number в процентных пунктах, дефолт 0. Ввод 30 означает 30%. При пустой марже категории формула Target ROAS ищет эту настройку по имени в колонке A. Непустая маржа категории заменяет общую. ### Funnel, benchmark и priority

#### `product_type_id_suffixes_to_strip`

Тип: string, дефолт пустой. Постфиксы Merchant ID через запятую для поиска категории во внешнем XML. Пример: Merchant `123_ru`, XML `123`, настройка `_ru`. Не используется при обычном чтении product type из custom label и не объединяет статистику.

### Точный алгоритм внешнего сопоставления категорий

`findExternalProductTypeMatch_` сначала ищет полный нормализованный Merchant ID во внешней карте. При отсутствии совпадения пробует каждый указанный префикс, совпавший с началом ID. Затем пробует постфиксы сначала у полного ID, затем у вариантов без префикса.

Префикс/постфикс сравнивается без учёта регистра только на соответствующем краю строки; середина ID не заменяется. Побеждает первое найденное совпадение. Рекурсивного удаления произвольного количества префиксов/постфиксов нет.

Внешние ID при загрузке нормализуются, но заданные префиксы и постфиксы с них не обрезаются. Пример в обратную сторону, где Merchant `123`, а XML `UA123`, этим механизмом не решается.

При нескольких XML первая найденная запись нормализованного ID остаётся в общей карте. Если внешний источник включён, но совпадение товара не найдено, `product.productTypes` становится пустым массивом: автоматического возврата к Merchant product type в этой ветке нет.

Категория меняется только внутри расчёта скрипта. Скрипт не записывает product_type обратно в Merchant; в Products выводятся ID, исключения и метки. По ID `123`, `UA123`, `123_ru` статистика остаётся раздельной.

Включает чтение предыдущего состояния воронки и attribution из `ProductDiagnostics` или `Products`. ID, флаг карантина и дата его последнего выхода читаются из диагностики отдельно и независимо от этой галочки.

#### `enable_sheet_protection`

Включает обновление защиты служебных листов. FALSE не снимает ранее поставленную защиту остальных листов. У Seasonality доступная скрипту защита снимается отдельно независимо от переключателя.

Открытыми остаются:

- `ProductTypes`;
- `Dashboard`;
- `DashboardData`;
- `Priorities`;
- `Seasonality`;
- `Settings`.

#### `enable_products_write`

Если `FALSE`, код не записывает `Products`, но проверяет наличие старых строк допфида. Пустой Products в обычном запуске вызывает ошибку.

#### `write_chunk_size`

Количество строк одного блока `setValues` при записи Products и полной ProductDiagnostics. Не размер страницы Merchant API и не размер группы ID карантинного запроса.

#### `product_diagnostics_start_row`

Позволяет писать `ProductDiagnostics` не с первой строки данных.

#### `auto_register_gcp_project`, `developer_email`, `wait_after_gcp_registration_seconds`, `merchant_api_page_size`, `merchant_api_retry_count`, `merchant_api_retry_sleep_seconds`

Служебные настройки Merchant API и повторов.

### Процентные поля при генерации

`spend_to_price_threshold` и `target_cpa_excess_threshold` получают формат `0%` по названию ключа. Дефолты 0.30 и 0.20 видны как 30% и 20%. Форматирование не изменяет хранимое число и не округляет его для вычислений: дробные доли процента могут сохраняться, даже если отображение без десятичных знаков.

Перестановка строк не меняет адресацию этих полей: при пересборке ключ снова получает нужный формат. Существующее значение 0 не заменится на новый дефолт 20%, потому что настройки сначала читаются из старого листа.

### Форматирование Settings

Колонка A содержит ключи, колонка B значения, колонка C комментарии.

Комментарии пишутся на украинском.

Boolean-настройки получают checkbox validation.

Ручные значения в колонке B подсвечиваются жёлтым, кроме ключей `isSettingsServiceKey_`: auto_register_gcp_project, developer_email, wait_after_gcp_registration_seconds, merchant_api_page_size и default_benchmark_group. Это отдельный список оформления, не весь последний служебный блок: многие настройки в нём тоже остаются жёлтыми.

Обязательные ключи подсвечиваются красным.

## 11. Расширенный справочник по потоку данных

Этот раздел нужен как рабочая инструкция: по нему можно объяснять, что именно делает скрипт во время запуска и как данные переходят между листами.

### Общий порядок полного запуска

1. Проверяет базовую ссылку `SPREADSHEET_URL`, открывает таблицу и проверяет локаль.
2. Читает Settings по именам ключей и пересобирает шаблон, сохраняя прочитанные значения известных настроек.
3. Выполняет runtime-валидацию, проверяет подключение сервисов Merchant API и регистрацию проекта.
4. Создаёт недостающие листы, мигрирует Priorities, оформляет его заголовки; выставляет первые три листа.
5. Снимает доступную скрипту защиту Seasonality.
6. При `enable_dashboard_from_diagnostics=TRUE` переходит в отдельный режим Dashboard и заканчивает обычный маршрут. Подготовка Settings и API-сервисов выше уже выполнена, но каталог Merchant не читается.
7. В обычном режиме загружает страницы товаров Merchant, применяя локальные фильтры к каждой полученной странице. При пустой итоговой выборке останавливается с ошибкой до записи Products.
8. Если задан внешний XML, подменяет категории его данными; строит карту Merchant по нормализованному ID.
9. Всегда читает из диагностики ID, прежний флаг карантина и дату последнего выхода.
10. При включённом чтении прошлого состояния дополнительно читает воронку и attribution из диагностики; если карта пуста, пробует Products.
11. Ручные значения ProductTypes читаются независимо от фильтров и карантина. Если нужны фильтр категорий, сезонность или правило CPA, сохраняется полный расчёт 30-дневной статистики и запись листа. Иначе дерево для benchmark/priority готовится только в памяти без запроса статистики и без перезаписи ProductTypes.
12. Читает ручную сезонность и Priorities.
13. Загружает окно воронки, если включена воронка или карантин. При совпадении с уже загруженными 30 днями использует имеющуюся карту.
14. При включённом карантине читает registry/history, отключает неактивные правила, определяет фактические выходы, получает статистику правил и ограничивает её индивидуальными датами. Собирает кандидатов и записывает registry/history.
15. При отключённом карантине использует пустую активную карту и отмечает выход ранее активных товаров в карте дат.
16. Формирует общие `outputRows`: решения исключения, показатели воронки, приоритеты, карантинные показатели и attribution.
17. При отключённой полной диагностике или частичной записи отдельно сохраняет три карантинных поля для всех текущих товаров.
18. Пересобирает Seasonality, возвращая ручные значения по ID.
19. Если запись Products включена, записывает допфид; иначе проверяет наличие прежних строк Products.
20. Если полная диагностика включена, записывает её целиком либо с заданной позиции. Дата выхода переносится в карантинный блок.
21. Если нужен хотя бы один дашбордный выход, получает или переиспользует общие периоды 14/30 дней. DashboardData и Dashboard обновляет по отдельным переключателям.
22. Повторно выставляет первые три листа, скрывает пустые стандартные листы.
23. При включённой защите обновляет её на управляемых листах; записывает итоговые логи.

### Что считается ручными листами

Ручные или частично ручные листы:

- `Settings`;
- `ProductTypes`;
- `Seasonality`;
- `Priorities`;
- `Dashboard`, если пользователь сделал кастомный layout.

Служебные листы:

- `Products`;
- `DashboardData`;
- `ProductDiagnostics`;
- `QuarantineRegistry`;
- `QuarantineLog`.

### Что скрипт должен сохранять между запусками

`ProductTypes`:

- галочку `Вмикаємо`;
- `benchmark_label`;
- `priority_label`;
- сезонные галочки;
- `target_cpa`;
- `margin_percent`;
- числовой ручной `target_roas` (не вычисленное значение формулы);
- `comment`.

`Seasonality`:

- потоварные сезонные галочки;
- комментарий.

`Priorities`:

- все ручные ID;
- все ручные `priority_group`;
- комментарии `comment`.

`ProductDiagnostics`:

- previous state;
- историю funnel stage;
- attribution-поля, если включено чтение предыдущего состояния;
- общую дату выхода из карантина и признак его активности для сопоставления между запусками.

`QuarantineLog`:

- агрегированный счётчик попаданий товара в карантин.

### Что скрипт может перезаписать полностью

`Settings`:

- шаблон листа пересобирается при каждом запуске;
- значения известных настроек сначала читаются и потом возвращаются в новый шаблон.

`ProductDiagnostics`:

- при `product_diagnostics_start_row=1` лист очищается по содержимому и записывается заново.

`DashboardData`:

- содержимое очищается и строится заново.

`QuarantineRegistry`:

- строки данных очищаются и заменяются текущими активными карантинами.

`QuarantineLog`:

- строки данных очищаются и заменяются агрегированной историей.

`Seasonality`:

- содержимое пересобирается, но ручные значения подставляются из старого состояния.

`ProductTypes`:

- управляемая область пересобирается, но ручные значения подставляются из старого состояния.

`Products`:

- при обычном успешном построении строк допфид перезаписывается;
- если строк товаров не построилось, лист не трогается.

## 12. Подробно: Products как допфид

### Заголовки Products

`Products` всегда пишется как компактная таблица.

Первые три заголовка фиксированные:

- `id`;
- `excluded_destination`;
- `excluded_destination`.

Четвёртый заголовок берётся из Settings:

- ключ: `funnel_stage_output_attribute`;
- в тестовой таблице сейчас это `custom_label_0`.

Пятый заголовок берётся из Settings:

- ключ: `priority_output_attribute`;
- в тестовой таблице сейчас это `custom_label_4`.

Внутренний writer умеет не выводить priority-колонку при невалидном имени, но обычный запуск до него не дойдёт: runtime-валидация требует корректные и разные custom label для stage и priority.

### Как формируется строка Products

Для каждого товара код берёт одну строку из `outputRows`.

В строку `Products` попадает:

- ID товара;
- значение для Shopping excluded destination;
- значение для Display excluded destination;
- funnel stage;
- priority group.

### Откуда берётся ID

ID приходит из Merchant API.

Код сохраняет ID в `offerId`.

Для сравнения ID в картах используется нормализованный ID `normId`.

В сам `Products` пишется исходный Merchant ID, а не нормализованная версия.

### Откуда берётся Shopping excluded destination

Колонка B заполняется только если товар исключён.

Исключение считается по общему списку причин.

Если причин нет, ячейка пустая.

Если причины есть, пишется Settings `shopping_excluded_value`.

### Откуда берётся Display excluded destination

Колонка C работает так же, как колонка B.

Если товар исключён, пишется Settings `display_excluded_value`.

Если товар не исключён, ячейка пустая.

### Откуда берётся funnel stage

Funnel stage считается в блоке Funnel Builder.

Для расчёта используются:

- impressions;
- clicks;
- conversions;
- benchmark group;
- пороги benchmark group.

Стадия записывается в рабочую строку товара.

Потом `writeProductsSheet_` переносит её в колонку D.

### Откуда берётся priority group

Priority group выбирает функция `choosePriorityLabel_`.

Порядок источников строгий:

1. `Priorities`;
2. `ProductTypes`;
3. Merchant API;
4. `other`.

### Что значит источник Priorities

Если на `Priorities` есть строка:

- `id` равен ID товара;
- `priority_group` не пустой;

то это значение берётся в первую очередь.

Категория товара и Merchant custom label в этом случае игнорируются для priority.

### Что значит источник ProductTypes

Если на `Priorities` для товара нет значения, код смотрит `ProductTypes`.

Код ищет самый глубокий совпадающий путь категории с заполненным `priority_label`.

Если товар лежит в категории, для которой найден `priority_label`, это значение становится priority group товара.

### Что значит источник Merchant API

Если нет priority на `Priorities` и нет priority на `ProductTypes`, код читает Merchant API.

Какое поле читать, задаёт Settings `priority_label_field`.

Например:

- `custom_label_4`;
- `custom_label_3`;
- имя custom attribute.

### Что значит fallback other

Если priority не найден нигде, код пишет `other`.

Это нужно, чтобы товары без явного приоритета всё равно попадали в понятную группу.

### Когда Products не перезаписывается

Если после чтения и расчётов `rows.length === 0`, код не пишет заголовки, не чистит хвост и не меняет лист.

Это защита от пустого допфида.

Если товары есть, лист обновляется.

### Как чистится хвост Products

После записи новых строк код очищает строки ниже последней записанной строки.

Очищается только управляемая ширина:

- минимум 5 колонок;
- или фактическая ширина output.

### Формула порогов и этапов воронки

`calculateFunnelRows_` допускает к расчёту порогов и сегментов только ID, присутствующие в отфильтрованной карте Merchant. Исходная карта Ads не изменяется. Пороги строятся отдельно для групп товаров без положительных конверсий; для кликов и показов считаются среднее всех участвующих значений и среднее положительных значений.

```text
threshold = ceil((avgAll + avgPositive) / 2)
high = есть различающиеся положительные значения
       AND value > avgAll
       AND value >= threshold
```

Если положительных значений нет или все они одинаковы, высокий сегмент не выделяется и диагностический порог пишется 0. Товары с продажами исключаются из расчёта порога, но получают свои сегменты при итоговой классификации.

Этап выбирается в порядке:
1. conversions > 0: `1 продажі`.
2. clicks = 0 и impressions = 0: `6 без стат`.
3. Высокие клики и показы: `2 вк+вп`.
4. Высокие клики и низкие показы: `3 вк+нп`.
5. Низкие клики и высокие показы: `4 нк+вп`.
6. Остальные: `5 нк+нп`.

Это классификация окна `funnel_days_ago`, не последовательное обязательное прохождение каждого этапа товаром. Исключения и карантин считаются отдельно: товар может иметь этап продаж и одновременно исключаться.

### ID и область объединения статистики

Merchant сохраняет исходный offerId для выхода. Карты скрипта используют `normOfferId_`, а Ads-агрегаты собираются по product item ID. Префиксы и постфиксы внешних категорий не участвуют в этом ключе.

Разные полные ID дублей остаются разными ключами. При одинаковом нормализованном ID карта не разделяет товары дополнительно по feed label или языку; это не отдельная система объединения дублей через настройки обрезания.

Внешний product type подменяется уже после чтения Merchant. Merchant benchmark/priority к этому моменту прочитаны в объект товара; ручные категорийные правила затем могут переопределить их. Автоматическое заполнение пустых меток ProductTypes найденными Merchant-значениями не реализовано и по решению пользователя не добавляется.

## 13. Подробно: Priorities

### Зачем нужен Priorities

`Priorities` нужен для ручного списка товаров, который клиент передаёт отдельной таблицей.

Этот лист заменяет необходимость делать отдельный внешний допфид только ради списка ID с приоритетами.

### Как создаётся лист

Код смотрит Settings `priority_sheet_name`.

Если настройка пустая, используется `Priorities`.

Если лист с таким именем есть, используется он.

Если листа нет, но есть старый лист `ClientPriority`, он переименовывается.

Если нет ни нового, ни старого листа, создаётся новый лист.

### Почему в коде ещё есть `ClientPriority`

Старое имя используется только для миграции тестовых таблиц.

Это не рабочее имя листа.

Рабочее имя после миграции: `Priorities`.

### Структура листа

Минимальная структура:

- колонка A: `id`;
- колонка B: `priority_group`;
- колонка C: `comment`.

Комментарий нужен человеку и не участвует в рекламных расчётах. Если при миграции C занята другим заголовком и `comment` нигде нет, перед C вставляется новая колонка. Если `comment` уже существует в другом месте, используется существующая колонка. Ручные данные не пересобираются.

### Колонка A: `id`

Заполняется вручную.

Обычно сюда вставляют список ID, полученный от клиента.

Код читает отображаемые значения.

Перед сравнением ID нормализуется.

### Колонка B: `priority_group`

Заполняется вручную.

Значение может быть любым текстом, который команда хочет передать как priority group.

Код не ограничивает список значений.

Пустая `priority_group` игнорируется.

### Что происходит с дублями ID

Код читает строки сверху вниз.

Если один ID встречается несколько раз, более поздняя строка перезапишет значение в карте.

В результате для товара останется последнее прочитанное значение.

### Что происходит с пустыми строками

Если `id` пустой, строка пропускается.

Если `priority_group` пустой, строка пропускается.

### Что скрипт пишет на Priorities

Скрипт пишет только заголовки, если их нет.

Скрипт не пишет ID товаров.

Скрипт не пишет priority group и текст комментариев.

Скрипт не очищает список. Сохранение комментария обеспечивается отсутствием перезаписи, а не копированием его в новый массив строк.

### Форматирование Priorities

Если включён `enable_managed_sheet_formatting`, код:

- красит заголовки A:B и колонки `comment` в синий;
- красит ручные области A:B и `comment` в жёлтый;
- замораживает первую строку.

### Защита Priorities

В `protectManagedSheets_` лист `Priorities` включён в список открытых листов.

Это значит, что скрипт не должен защищать его как служебный лист.

## 14. Подробно: ProductTypes

### Назначение ProductTypes

`ProductTypes` связывает товарный каталог с ручным управлением.

На этом листе команда управляет:

- включением категорий;
- benchmark label по категории;
- priority label по категории;
- сезонностью по категории;
- target CPA по категории;
- комментариями.

### Как код строит дерево

Сначала код собирает product type у каждого товара.

Потом каждый путь разбивается на уровни.

Путь ограничивается пятью уровнями (`settings.maxLevels = 5`).

Каждый уникальный путь добавляется в дерево.

Дерево обходится сверху вниз.

Строки выводятся в отсортированном порядке.

### Почему строки разреженные

Если строка соответствует первому уровню, значение пишется в `product_type_l1`.

Если строка соответствует второму уровню, значение пишется в `product_type_l2`, а первый уровень может быть пустым в отображении.

Так лист визуально показывает вложенность.

Технически полный путь хранится через `path_key`.

### Как сохраняется состояние

Перед пересборкой код читает старый лист.

Для каждой строки строится ключ пути.

По ключу сохраняются ручные значения.

После пересборки, если такой ключ снова появился, ручные значения возвращаются.

### Колонка `Вмикаємо`

Это ручная галочка.

Новая категория получает `TRUE`.

Существующая категория получает старое значение.

Используется только при включённом `enable_product_type_filter`.

Если фильтр выключен, товар проходит по категории независимо от галочки.

### Колонки `product_type_l1...product_type_l5`

Это уровни дерева категорий.

Количество уровней фиксировано: пять.

Всегда создаются `product_type_l1` ... `product_type_l5`. Старое значение `max_product_type_levels` на листе не управляет шириной дерева.

### Колонка `benchmark_label`

Это ручное значение.

Оно описывает группу, внутри которой считаются пороги кликов и показов.

Код читает эту колонку как категорийное правило.

Для товара применяется самое глубокое совпадение.

Если `benchmark_label` заполнен на родителе и на дочерней категории, дочернее значение сильнее.

### Колонка `priority_label`

Это ручное значение.

Оно описывает priority group для товаров категории.

Код читает эту колонку как категорийное правило.

Для товара применяется самое глубокое совпадение.

Если товар есть на `Priorities`, значение `priority_label` с категории не используется.

### Колонки `winter`, `spring`, `summer`, `autumn`

Это ручные категорийные галочки сезонности.

Если ни одна галочка в строке не включена, строка не создаёт сезонное правило.

Если хотя бы одна галочка включена, категория считается сезонно размеченной.

Для товара применяется самое глубокое совпадающее сезонное правило.

### Колонка `path_key`

Это техническая колонка.

Значение строится из полного пути категории.

Разделитель внутри ключа: `|||`.

Код использует ключ для сохранения ручных значений.

Колонка скрывается.

### Колонка `path_depth`

Это техническая колонка.

Она показывает глубину категории.

Код использует глубину для выбора самого глубокого правила.

Колонка скрывается.

### Колонка `has_season_rule`

Это техническая формула.

Формула проверяет сезонные галочки строки.

Колонка скрывается.

### Колонка `aov`

Источник: расчёт статистики по категории.

Для конечной категории значение считается по товарам категории.

Для родительской категории код учитывает дочерние AOV и собственные товары родителя.

### Колонка `conversions_30d`

Источник: Google Ads статистика за 30 дней.

Показывает конверсии категории.

### Колонка `spend_30d`

Источник: Google Ads статистика за 30 дней.

Показывает расходы категории.

### Колонка `actual_cpa_30d`

Источник: расчёт по `spend_30d` и `conversions_30d`.

Если конверсий нет, CPA равна 0.

Эта колонка дополнительно форматируется цветом относительно `target_cpa`.

### Колонка `conversion_value_30d`

Источник: Google Ads статистика за 30 дней.

Показывает ценность конверсий категории.

### Колонка `target_cpa`

Источник: ручной ввод.

Сохраняется по `path_key`.

Используется в двух местах:

- для подсветки `actual_cpa_30d`;
- для карантина `TARGET_CPA`.

### Колонка `comment`

Источник: ручной ввод.

Сохраняется по `path_key`.

На расчёты не влияет.

### Подсветка actual CPA

Если `target_cpa` пустой, нулевой или неположительный, для сравнения берётся `default_target_cpa`. Только если и общая цель не положительна, фон `actual_cpa_30d` белый.

Если `actual_cpa_30d` пустой или 0, фон белый.

Если `actual_cpa_30d > target_cpa`, фон светло-красный.

Если `actual_cpa_30d <= target_cpa`, фон зелёный.

### Логика включения категорий

Код не требует, чтобы были отмечены все родители.

Если отмечен второй уровень, а первый уровень не отмечен, второй уровень работает.

Если отмечен третий уровень, а первый и второй не отмечены, третий уровень работает.

Если отмечен родитель и внутри нет отмеченных детей, работает всё поддерево родителя.

Если отмечен родитель и внутри есть отмеченные дети, соседние неотмеченные ветки не проходят.

Товары, лежащие прямо в отмеченном родителе, проходят.

### Точный порядок колонок и пересборка ProductTypes

При пяти уровнях штатная структура содержит 25 колонок:

| Колонки | Заголовки | Роль |
| --- | --- | --- |
| A | `Вмикаємо` | Ручное разрешение категории |
| B:F | `product_type_l1` ... `product_type_l5` | Разреженное дерево |
| G:H | `benchmark_label`, `priority_label` | Ручные переопределения |
| I:L | `winter`, `spring`, `summer`, `autumn` | Сезонность категории |
| M:O | `target_cpa`, `target_roas`, `margin_percent` | Ручные цели и маржа; ROAS может быть формулой |
| P:R | `path_key`, `path_depth`, `has_season_rule` | Скрытые технические поля |
| S:T | `actual_cpa_30d`, `actual_roas_30d` | Фактические показатели, всегда начало статистического блока |
| U:X | `aov`, `conversions_30d`, `spend_30d`, `conversion_value_30d` | Штатный порядок остальных статистических полей |
| Y | `comment` | Ручной комментарий, всегда последний |

`buildProductTypesHeader_` фиксирует A:R. Actual CPA и actual ROAS всегда ставятся сразу за техническим блоком; комментарий всегда замыкает таблицу. Порядок остальных существующих хвостовых заголовков может сохраняться. Перестановка CPA/ROAS пользователем не задаёт новый постоянный порядок генератору.

Ручные цели, метки, сезоны и комментарий читаются по заголовкам. Путь восстанавливается из разреженных B:F через `applySparsePathRow_`, а не простым чтением номера строки. При одинаковом восстановленном ключе более поздняя строка заменяет прежнее сохранённое состояние.

Произвольные дополнительные заголовки могут переноситься в хвост, но `getProductTypesRowValue_` для неизвестного имени возвращает пустую строку. Сохранение значений пользовательских дополнительных колонок не реализовано; пользователь исключил такую поддержку из задач.

### Как именно рассчитывается статистика категорий

`getAdsStatsMap_(30, 0)` берёт 30 дней, включая сегодня. Ни `exclude_last_days`, ни дата выхода из карантина к этим показателям не применяются.

Для статистики выбирается первый путь из `product.productTypes`, хотя дерево может содержать несколько путей товара. Расходы, конверсии и ценность добавляются к каждому предку выбранного пути. Родительская строка уже включает дочерние товары: суммировать все строки дерева между собой нельзя, иначе появится повторный учёт.

`actual_cpa_30d = cost / conversions` при положительных конверсиях, иначе 0. `actual_roas_30d = roasConversionValue / cost` при положительных расходах, иначе пустая ячейка. Ценность для ROAS родителя включает дочерние категории.

AOV конечной категории - средняя положительная цена товаров из Merchant. AOV родителя - среднее положительных AOV непосредственных дочерних групп, плюс отдельная группа собственных конечных товаров родителя, если она есть. Это не средний чек по заказам и не взвешивание дочерних AOV по количеству продаж.

### Общий Target CPA и ручное значение категории

`applyProductTypesTargets_` не копирует общую цель в жёлтую ячейку. Она остаётся пустой, пока человек не задаст категорийное значение.

Для каждой строки в памяти строится `effectiveTargetCpa`: положительный ручной `target_cpa`, иначе `default_target_cpa`. Только положительные эффективные значения становятся правилами. Затем товар получает самое глубокое совпадающее правило по своим путям.

Важная особенность: общий fallback подставляется в каждую строку до выбора глубочайшего правила. Поэтому пустая дочерняя строка при заданной общей цели создаёт своё правило с общей целью; это не безусловное наследование ручной цели родителя. Если общая цель 0, пустая дочерняя строка правила не создаёт и может действовать положительная цель родителя.

Если подходящего положительного категорийного правила нет, chooseProductTypeTargetCpa_ использует положительный default_target_cpa из Settings, включая товар без категории. Одна функция выбирает цель для карантина и диагностики. Если обе цели отсутствуют, правило не срабатывает.

### Колонка target_roas: ручное значение и формула

`readProductTypeManualStateMap_` читает и значения, и формулы колонки. Число без формулы сохраняется как ручная цель. Вычисленное значение формулы не становится ручным переопределением.

Если сохранённая ручная цель положительна, генератор возвращает её как число. Иначе записывает новую формулу:
- берёт `margin_percent` этой строки, если ячейка непустая;
- при пустой марже ищет `default_margin_percent` по имени в колонке A Settings через INDEX/MATCH;
- при марже больше 0 и не больше 100 возвращает `100 / margin`;
- при непригодной марже или ошибке возвращает пустую строку.

Маржа 30 даёт коэффициент 3.3333..., отображаемый как 333.33%. Ручные 400% хранятся как 4 и сильнее расчёта по марже. Очистка ручной цели возвращает формулу на следующем прогоне. Произвольная пользовательская формула не сохраняется как отдельное правило: генератор заменяет её своей формулой.

Формула реагирует на изменение маржи в таблице; цвет actual ROAS ставится скриптом при форматировании, а не условным форматированием в реальном времени.

### Колонка margin_percent и единицы измерения

`margin_percent` хранит процентные пункты: число 30 означает маржу 30%. Формат `0.00"%"` добавляет знак процента к числу, но не умножает его на 100. Общая `default_margin_percent` тоже читается как 30, а не 0.30.

Пустая категорийная маржа означает общую из Settings. Непустой 0 не равен пустой ячейке: он не включает fallback, и автоматический Target ROAS будет пустым. Маржа не наследуется от родителя дерева.

Это отличается от `target_roas`, `actual_roas_30d` и двух процентных порогов карантина: те используют обычный процентный формат и хранят долю/коэффициент.

### Подсветка actual ROAS и сохранение жёлтой заливки

Actual ROAS выше положительной цели - зелёный; ниже - светло-красный; равен цели, отсутствует или цель неположительна - белый. Нулевой ROAS при наличии расходов и положительной цели ниже цели и красный. Actual CPA при равенстве цели зелёный, поэтому границы подсветки CPA и ROAS различаются.

`applyProductTypesBaseBackgrounds_` назначает итоговую базовую заливку всей области: синий заголовок, жёлтые ручные поля, стандартный фон остальных ячеек. В том числе жёлтыми остаются Target ROAS и Margin Percent. Промежуточное обнуление фона всей области удалено; содержимое и проверки данных при пересборке по-прежнему очищаются и создаются заново.

Жёлтый цвет означает доступное человеку поле, но не гарантирует, что там только ручное число: Target ROAS может содержать формулу. ROAS и маржа не добавляют отдельный карантин и не меняют этап воронки; карантин дорогого CPA по-прежнему сравнивает CPA с его целью.

### Назначение Seasonality

Также этот лист показывает категорийную сезонность, подтянутую из `ProductTypes`.

Итоговые сезонные колонки используются для исключения товара.

### Как сохраняются ручные значения

### Колонки `product_type_l1...product_type_l5`

### Колонка `category_summer`

Источник: формула.

Формула ищет подходящую категорию на `ProductTypes`.

Колонка скрывается.

Источник: формула.

Формула ищет подходящую категорию на `ProductTypes`.

### Приоритет потоварной сезонности

Если у товара есть хотя бы одна ручная сезонная галочка, категорийная сезонность для него не используется.

Это значит, что товарные галочки переопределяют категорийные.

Если ручных галочек нет, работает категорийная сезонность.

Если нет ни ручной, ни категорийной сезонности, товар считается включённым.

### Видимые чекбоксы

Видимые ручные boolean-поля:

- `manual_winter`;
- `manual_spring`;
- `manual_summer`;
- `manual_autumn`.

На них ставится checkbox validation.

Расчётные boolean-поля скрываются как вспомогательные. Формулы возвращают логические значения; отображение чекбоксами не меняет расчёт. В проверенной пользователем существующей таблице после раскрытия этих колонок отображались галочки. Генератор явно устанавливает checkbox validation на четыре ручные колонки; это не равнозначно гарантии создания checkbox validation на всех восьми расчётных колонках новой таблицы.

### Активные сезоны Settings и продление сезона

ProductTypes отвечает на вопрос «каким сезонам относится категория», Seasonality - «есть ли у товара собственное переопределение», четыре галочки Settings - «какие сезоны сейчас разрешены».

Календарь не включает текущий сезон автоматически. Можно одновременно отметить лето и осень: товар проходит сезонный фильтр, если хотя бы один его эффективный сезон отмечен. Так разрешаются летние товары осенью. Остальные ограничения, включая карантин, остаются.

При включённом фильтре и всех выключенных активных сезонах размеченные сезонные товары не проходят; товары без сезонной разметки проходят. При отключённом фильтре сезонность не исключает товары, но сам Seasonality всё равно пересобирается.

### Формулы, индексы и защита Seasonality

Полный путь и пять уровней writer берёт через `getOutputRowIndexes_`, а не старые смещённые позиции. Формулы категорийной сезонности используют I:L ProductTypes и технические P:R после добавления трёх целевых полей.

При пяти уровнях Seasonality: A:C - ID/название/полный путь; D:H - уровни; I:L - ручные сезоны; M:P - категорийные; Q:T - итоговые; U - комментарий. M:T скрываются при форматировании.

`removeProtectionsForSheet_` вызывается при подготовке листов и при форматировании Seasonality. Снимаются защиты листа и диапазонов, которые скрипт вправе изменить. В общем обработчике защиты Seasonality внесён в открытые листы. Автоматически возвращать замок этот маршрут не должен; переключатель общей защиты этого не меняет.

## 16. Подробно: карантин

### Общая модель карантина

Карантин работает как набор независимых правил.

Каждое правило может добавить товар в кандидаты.

Если у товара сработало несколько правил, причины объединяются.

Для каждой причины хранится отдельная дата выхода.

Общая дата выхода `active_until` равна максимальной дате по активным причинам.

### Правило NO_SALES

Настройки:

- `enable_no_sales_rule`;
- `clicks_threshold`;
- `no_sales_lookback_days`;
- `no_sales_quarantine_days`.

Источник данных: отдельный Google Ads stats запрос.

Товар попадает в правило, если:

- clicks больше `clicks_threshold`;
- conversions равны 0.

### Правило SPEND_OVER_MARGIN

Настройки:

- `enable_spend_rule`;
- `spend_lookback_days`;
- `spend_to_price_threshold`;
- `spend_quarantine_days`.

Источник данных:

- cost, conversions, conversion value из Google Ads;
- price из Merchant API.

Товар попадает в правило, если расход достиг лимита от цены.

Лимит:

`price * spend_to_price_threshold`.

Дополнительное условие:

- нет конверсий или нет conversion value;
- или conversion value есть, но расходы выше conversion value.

### Правило EXPENSIVE_CLICK

Настройки:

- `enable_expensive_click_rule`;
- `expensive_click_threshold`;
- `expensive_click_quarantine_days`.

Код фактически берёт статистику одним вызовом:

`getAdsStatsMap_(1, 1)`.

Это один день со сдвигом на 1 день.

Товар попадает в правило, если:

`cost / clicks >= expensive_click_threshold`.

### Правило TARGET_CPA

Настройки:

- `enable_target_cpa_rule`;
- `target_cpa_lookback_days`;
- `target_cpa_excess_threshold`;
- `target_cpa_quarantine_days`.

Источник данных:

- cost и conversions из Google Ads за период `target_cpa_lookback_days`;
- `target_cpa` из `ProductTypes`.

Товар попадает в правило, если:

- у него есть Merchant product;
- по категории найден target CPA;
- conversions больше 0;
- actual CPA выше лимита.

Actual CPA:

`cost / conversions`.

Лимит:

`categoryTargetCpa * (1 + target_cpa_excess_threshold)`.

Если `target_cpa_excess_threshold=0`, любое превышение target CPA отправляет товар в карантин.

### Что происходит при отключении правила

`applyEnabledQuarantineRules_` сбрасывает флаг и дату причины, если соответствующее правило выключено в Settings.

Если выключен `enable_target_cpa_rule`, очищаются:

- `targetCpa`;
- `targetCpaUntil`.

### Как считается активность карантина

Товар активен, если `active_until` не пустой и дата ещё активна.

Истёкшие записи не попадают в активную карту.

`QuarantineRegistry` записывает только активные на сегодня товары.

### Дефолты и точные условия срабатывания

Это дефолты генератора, а не утверждение о значениях конкретного проекта. Сохранённые значения Settings не заменяются новыми дефолтами.

| Правило | Дефолт включения | Данные до индивидуального ограничения | Условие | Срок |
| --- | --- | --- | --- | --- |
| NO_SALES | TRUE | 30 дней, исключены сегодня и вчера | clicks > 100 и conversions = 0 | 7 дней |
| SPEND_OVER_MARGIN | TRUE | 30 дней, исключены сегодня и вчера | cost >= price × 0.30 и нет возврата либо cost > conversionValue | 7 дней |
| EXPENSIVE_CLICK | TRUE | Только вчера | clicks > 0 и cost / clicks >= 100 в валюте Ads | 7 дней |
| TARGET_CPA | TRUE | 30 дней, исключены сегодня и вчера | conversions > 0, цель положительна, cost / conversions > цель × 1.20 | 7 дней |

«Нет возврата» в SPEND_OVER_MARGIN означает conversions = 0 **или** conversionValue <= 0. Вторая ветка требует положительной conversionValue и cost > conversionValue. Нужна положительная цена Merchant. Несмотря на внутреннее имя SPEND_OVER_MARGIN, порог привязан к цене товара, а не к полю маржи ProductTypes.

NO_SALES использует строго больше 100, не «от 100». SPEND_OVER_MARGIN и EXPENSIVE_CLICK срабатывают и при равенстве порогу. TARGET_CPA использует строго больше лимита: при цели 200 и допуске 20% значение 240 само по себе ещё не срабатывает, выше 240 - срабатывает.

Для дорогого CPA нет отдельного минимального количества конверсий, кроме условия больше 0. Для дорогого клика не требуется отсутствие продаж: проверяется средний CPC вчерашнего дня, а не цена отдельного клика.

### Плановая дата и фактический выход: два разных поля

При добавлении причины срок рассчитывается как дата текущего запуска плюс число дней карантина. `isDateActive_` проверяет строго `until > today`. Например, добавление 1 сентября на 7 дней даёт границу 8 сентября: начиная с 8 сентября прежняя запись уже не активна.

`active_until` / `quarantine_release` - плановая максимальная граница причин текущей паузы. `last_quarantine_exit_date` - дата, когда обычный запуск обнаружил, что раньше товар был в карантине, а теперь не активен.

Если скрипт не работал в плановый день выхода и вернулся позже, фиксируется день обнаружения, а не восстанавливается пропущенная дата задним числом. Новое поле не означает, что Merchant уже успел обработать допфид или товар фактически начал получать показы.

### Как определяется единая дата выхода

`readQuarantineLifecycle_` ищет три заголовка в ProductDiagnostics: `id`, `quarantine_active`, `last_quarantine_exit_date`. ID нормализуется; YES/TRUE распознаются как прежняя активность. Поддерживаются даты Sheets и текстовые даты через `parseDateFlexible_`.

В `updateQuarantine_` сначала читается registry, затем удаляются причины выключенных правил и пересчитывается `activeUntil`. Только после этого `updateQuarantineExitDates_` определяет выход, ещё до повторного сбора кандидатов.

Для ID, найденного только в registry, создаётся запись жизненного цикла с прежней активностью. Если прежний флаг активен и актуальной активной записи нет, сохраняется сегодняшняя дата. Если хотя бы одна причина ещё держит товар в карантине, дата выхода не обновляется.

Дата общая для всех четырёх правил, а не отдельная для каждой причины. Она не меняется при каждом обычном запуске активного в рекламе товара. При следующем новом выходе заменяется новой датой. У товара без известной истории выхода поле пустое.

При `enable_quarantine=FALSE` обычный маршрут передаёт пустую активную карту, поэтому прежние активные товары получают дату обнаруженного выхода. Сам registry в этой ветке не пересобирается. Если выключено только одно правило, оставшиеся активные причины могут продолжать удерживать товар.

### Итоговая формула индивидуального периода

Обозначения: `T` - дата запуска, `N` - период правила, `E` - число исключённых последних дней, `D` - сохранённая дата выхода.

```text
end = T - E
usualStart = end - (N - 1)
start = D существует ? max(usualStart, D) : usualStart
```

Обе границы запроса включены. Для NO_SALES, SPEND_OVER_MARGIN и TARGET_CPA используется общий E; для EXPENSIVE_CLICK всегда N=1, E=1.

Если start > end, доступных дней пока нет: прежняя статистика ID удаляется из карты правила, новый запрос для этого ID не выполняется. В диагностике показатели этого правила будут нулевыми, а не старой суммой.

Если D <= usualStart, индивидуальное ограничение уже ничего не меняет: остаётся обычное N-дневное окно. Дата при этом не удаляется из диагностики автоматически.

Пример: выход 9 сентября, N=30, E=2. На 9 и 10 сентября доступного нового дня нет. На 11 сентября учитывается 9 сентября. На 12 сентября - 9 и 10 сентября. Затем окно растёт до 30 доступных дней и снова становится обычным скользящим окном. Клики 1 сентября в него не возвращаются.

### Как меняются запросы и где хранятся данные

Сначала код получает общие агрегаты каждого включённого правила прежним способом. Затем `applyQuarantineDateWindows_` находит товары, чья дата выхода позже обычного начала окна.

Для таких товаров старая сумма удаляется из карты. Товары группируются по дате начала, ID сортируются и разбиваются на группы до 200. Для группы выполняется один запрос Google Ads с общими датами и списком ID, а не отдельный запрос на каждый товар.

Запрос использует `shopping_performance_view`: ID товара, показы, клики, cost_micros, конверсии и ценность. Расход делится на 1 000 000. Строки суммируются по нормализованному ID, результат **заменяет** старую сумму правила.

Кэш живёт только в текущем запуске. Ключ включает начало, конец и точный список ID; полностью совпавший запрос переиспользуется между правилами. Дневная статистика на лист не складывается, отдельный служебный лист дат не создаётся.

Дополнительные запросы могут увеличивать время запуска; механизм не обещает отсутствие нагрузки. Ошибка этого запроса не подменяется старой 30-дневной статистикой: исключение прерывает запуск. Исходные общие запросы продолжают выполняться, поэтому это не оптимизация их полного исключения.

### Какие показатели обрезаются, а какие нет

В существующих колонках диагностики ограничение применяется к кликам/конверсиям NO_SALES; расходам, конверсиям и ценности SPEND_OVER_MARGIN; CPC EXPENSIVE_CLICK; расходам, конверсиям и CPA TARGET_CPA.

Цена Merchant, пороги настроек и выбранная категорийная цель не являются историческими счётчиками и датой не обрезаются.

Общие показы, клики, расходы, конверсии и ROAS в блоке воронки сохраняют своё окно. Статистика ProductTypes за 30 дней и общие сводки DashboardData за 14/30 дней тоже не обрезаются.

Выход из карантина не назначает этап «Продажи» сам по себе. Он снимает карантинное исключение; этап отдельно зависит от конверсий в окне воронки. Сезонность или запрет категории могут по-прежнему исключать товар.

### Повторные кандидаты и сохранение истории

У уже активной записи повторное выполнение условий не увеличивает count и не переносит сроки: обновление кандидата находится внутри условия `!wasActive`. Несколько причин объединяются при новом добавлении кандидата; текущая реализация не дописывает новую причину уже активной записи в этом блоке.

Registry выводит только активные записи; QuarantineLog хранит агрегированные ID/count/last_added/problematic. Дата последнего выхода хранится в ProductDiagnostics и не удаляется при ограничении строк QuarantineLog.

При полной диагностике в новый лист попадают текущие товары: долговременное сохранение даты для товара, исчезнувшего из выборки Merchant, отдельно не реализовано. При записи только трёх полей существующие строки сохраняются. Это разные режимы, не гарантия вечной истории любого ID.

Проверка жизненного цикла в локальных сценариях не равна проверке фактического выхода на живом проекте. Последняя остаётся отложенной до соответствующего события.

## 17. Подробно: QuarantineRegistry

### Назначение

Лист показывает текущие товары на паузе.

По нему можно ответить клиенту:

- какие товары сейчас в карантине;
- по какой причине;
- когда они выйдут.

### Структура записи

Одна строка соответствует одному товару.

Если причин несколько, они хранятся в разных reason-колонках.

Срок выхода по каждой причине хранится отдельно.

### `id`

Источник: ID товара.

Пишется как видимый ID для проверки человеком.

### `reason_no_sales`

Источник: флаг причины `NO_SALES`.

Пишется `YES`, если причина активна.

### `reason_spend`

Источник: флаг причины `SPEND_OVER_MARGIN`.

Пишется `YES`, если причина активна.

### `reason_expensive_click`

Источник: флаг причины `EXPENSIVE_CLICK`.

Пишется `YES`, если причина активна.

### `quarantine_count`

Источник: история попаданий товара в карантин.

Увеличивается на 1 при попадании в кандидаты, только если прежняя запись товара не активна. Повторная проверка уже активного товара счётчик не увеличивает.

### `problematic`

Источник: сравнение `quarantine_count` и `problem_threshold`.

Пишется `YES`, если счётчик достиг порога.

### `active_until`

Источник: максимальная дата выхода по причинам.

Используется для понимания, до какого дня товар выключен.

### `no_sales_until`

Источник: дата выхода по причине `NO_SALES`.

### `spend_until`

Источник: дата выхода по причине `SPEND_OVER_MARGIN`.

### `expensive_click_until`

Источник: дата выхода по причине `EXPENSIVE_CLICK`.

### `last_added`

Источник: дата последнего попадания в карантин.

### `reason_target_cpa`

Источник: флаг причины `TARGET_CPA`.

Пишется `YES`, если причина активна.

### `target_cpa_until`

Источник: дата выхода по причине `TARGET_CPA`.

### Физический порядок QuarantineRegistry

A `id`; B `quarantine_count`; C `reason_no_sales`; D `reason_spend`; E `reason_expensive_click`; F `problematic`; G `active_until`; H `no_sales_until`; I `spend_until`; J `expensive_click_until`; K `last_added`; L `reason_target_cpa`; M `target_cpa_until`.

Чтение registry позиционное в ширине 13 колонок, не произвольное сопоставление по заголовкам. Ручная перестановка его колонок не поддерживается.

При записи registry каждый reason-флаг проверяется вместе с собственной датой, как в активной карте диагностики. Завершённые причины не получают YES; даты сохраняются для справки. Выключение всего карантина по-прежнему не пересобирает реестр.

### Перезапись листа

Код очищает старые строки данных в управляемой ширине.

Потом пишет только активные строки.

Истёкшие товары не остаются в текущем registry.

## 18. Подробно: QuarantineLog

### Назначение

`QuarantineLog` нужен для исторического анализа проблемных товаров.

Это не текущий список выключенных товаров.

### Структура

В текущем коде лог агрегированный.

Он хранит:

- `id`;
- `quarantine_count`;
- `last_added`;
- `problematic`.

### `id`

Источник: товар, который когда-либо попадал в карантинную историю.

### `quarantine_count`

Источник: сохранённый агрегированный count по ID. При обновлении выбирается максимум прежнего и переданного count; это не отдельная строка на каждое событие.

### `problematic`

Источник: сравнение счётчика с `problem_threshold`.

### `last_added`

Источник: дата добавления, переданная при обновлении истории. Хранится в третьей колонке; используется для справки, но не для сортировки лимита.

### Порядок и смысл истории

Строки сортируются по count по убыванию, затем по ID естественным порядком. Лимит оставляет первые строки этой сортировки, а не обязательно самые свежие события. Надпись Settings о «последних событиях» не описывает фактическую сортировку.

При чтении история дополняется registry, если там count больше. При каждом новом входе берётся максимум сохранённого count из registry и истории, затем добавляется 1 и результат сохраняется в обоих листах. Уже активный карантин и несколько одновременных причин не добавляют повторных единиц. Ранее потерянные события автоматически не восстанавливаются; удалённая по лимиту или вручную история не является бессрочным архивом.

### Лимит строк

Если `quarantine_log_max_rows=1000`, код оставляет до 1000 строк данных.

Если значение 0, лимит не применяется.

### Перезапись

Код очищает старые строки данных.

Потом записывает актуальную агрегированную историю.

## 19. Подробно: ProductDiagnostics

### Назначение диагностики

`ProductDiagnostics` показывает, почему скрипт принял решение по каждому товару.

Это основной лист для проверки:

- stage;
- benchmark;
- priority;
- product type;
- карантина;
- сезонности;
- причин excluded destination.

### Источник строк

Строки берутся из `outputRows`.

Это тот же массив, из которого формируется `Products`.

Поэтому диагностика и допфид должны описывать одни и те же товары.

### Физическая структура диагностики и преобразование строк

При пяти уровнях полный writer строит 77 заголовков. Три прежних выходных поля `category_match_id`, `product_type_source`, `product_type_status` больше не выводятся. Внутренние поля внешнего сопоставления могут существовать в объектах, но это не колонки текущего листа.

Внутри `outputRows` дата выхода добавляется последним элементом. Перед полной записью `remapDiagnosticsRows_` размещает её сразу после `quarantine_reasons`. Поэтому номера внутренних элементов после карантинного блока нельзя напрямую считать номерами колонок листа.

| Колонки | Группа заголовков | Цвет |
| --- | --- | --- |
| A:I | ID, название, исключения, дата статуса, Merchant/feed | Синий |
| J:P | Полный/все пути и пять product type уровней | Жёлтый |
| Q:W | Общая статистика от impressions до roas | Синий |
| X:AA | Статусы и сегменты до funnel_stage | Жёлтый |
| AB:AF | Benchmark/priority и пороги | Синий |
| AG:AJ | Карантин, плановая граница, причины, фактический выход | Жёлтый |
| AK | category_allowed | Синий |
| AL:AM | NO_SALES | Жёлтый |
| AN:AR | SPEND_OVER_MARGIN | Синий |
| AS:AT | EXPENSIVE_CLICK | Жёлтый |
| AU:AY | TARGET_CPA | Синий |
| AZ:BM | Сравнение с прошлым состоянием и даты attribution | Жёлтый |
| BN:BY | Накопленные attribution-поля шести этапов | Синий |

Группы задаёт `formatDiagnosticsHeaderGroups_` по именам начальных заголовков. Это заливка заголовков, не дополнительная строка и не объединённые ячейки. Синий `#cfe2f3`, жёлтый `#fff2cc`.

При чтении готовой диагностики для Dashboard дата возвращается в конец внутреннего массива. Этот remap сохраняет позиционные расчёты DashboardData после переноса видимой колонки. Формулы самого Dashboard находят показатели по именам заголовков.

### Полная, частичная и отключённая диагностика

При полной записи с первой строки writer очищает содержимое листа, пишет заголовки и строки блоками `write_chunk_size`. Форматирование вызывается при `enable_managed_sheet_formatting=TRUE`. В отличие от Products, полная диагностика не использует запись поверх старого листа без очистки.

При частичной записи исходный массив всё равно рассчитывается целиком, затем берётся `rows.slice(startDataRow - 1)`. Старые строки до этого места полной диагностикой не обновляются. Если дата выхода расположена после карантинного блока, колонка переносится туда физически; новые данные сопоставляются с заголовками листа.

При отключённой диагностике, а также перед частичной записью, `writeQuarantineLifecycle_` отдельно обновляет `id`, `quarantine_active`, `last_quarantine_exit_date`. Он ищет колонки по именам, добавляет отсутствующие заголовки, сопоставляет существующие строки по ID и добавляет новые ID в конец. Остальные колонки не пересчитывает и не очищает.

В этом сокращённом режиме ID и даты пишутся текстом. Дата остаётся на том же ProductDiagnostics, поэтому отключение полной диагностики не означает «на лист вообще ничего не пишется».

### Числовые форматы

Показы, клики, конверсии и соответствующие attribution-счётчики получают `0.##`. ROAS и spend_to_price_threshold - обычный `0.00%`. Денежные показатели, дорогой клик, цели CPA и attribution-ценность оформляются с кодом валюты Ads; код валюты сам по себе не выполняет конвертацию сумм.

`target_cpa_excess` - денежная разница actual CPA и базовой цели, не процент допуска. Поэтому она может быть положительной даже без карантина: например, CPA 220 при цели 200 и допуске 20% даёт excess 20, но лимит 240 ещё не превышен.

### Блок идентификации

#### `id`

Источник: Merchant API `offerId`.

#### `title`

Источник: Merchant API title.

#### `excluded_destination_shopping`

Источник: итоговое решение для Shopping excluded destination.

#### `excluded_destination_display`

Источник: итоговое решение для Display excluded destination.

#### `дата зміни статусу`

### Ограничения собственной attribution-модели

При наличии истории положительный прирост конверсий и ценности считается сравнением текущей суммы окна с прошлой. Уменьшение суммы обрезается до нуля. На первом запуске без истории вся накопленная ранее статистика не приписывается текущему этапу.

Когда прирост конверсий положителен, он относится к предыдущему сохранённому этапу, либо текущему/fallback при его отсутствии. Только рост ценности без роста количества конверсий не вызывает `addAttributionDelta_`.

`last_seen_*` записывают текущие значения для следующего запуска. `last_stage_change_date` меняется, когда есть непустой прошлый и текущий этап и они различаются. `last_conversion_attribution_date` меняется при положительном приросте конверсий.

Это сравнение агрегатов скользящего окна, а не привязка отдельных заказов к истории рекламных кликов. Дата выхода из карантина не сбрасывает эту attribution-историю.

### Отдельный режим Dashboard из готовой диагностики

В `enable_dashboard_from_diagnostics=TRUE` нет новых запросов каталога и обычного расчёта карантина/Products. Читается существующая диагностика, дата выхода возвращается во внутренний конец строки, из общих показателей строится карта stats.

Важный фактический нюанс: эта одна карта передаётся writer как для сводки 14 дней, так и для сводки 30 дней. Отдельной исторической статистики двух окон в этом режиме не загружается. Поэтому названия строк 14/30 дней не доказывают, что данные действительно собраны за разные периоды: значения наследуют окно и актуальность сохранённой диагностики.

Режим предназначен для уже полной диагностики. Сокращённый лист только из трёх карантинных полей не содержит всех требуемых показателей. Обычная подготовка Settings, проверка сервисов и регистрации выполняются до перехода в этот режим.

Первоначальное оформление включается, когда лист пустой по строкам и колонкам. В существующем листе содержимое пересобирается, а прежнее оформление в основном остаётся. Это не гарантирует автоматическую миграцию любых вручную испорченных форматов.

### Точный алгоритм внешнего сопоставления категорий

`findExternalProductTypeMatch_` сначала ищет полный нормализованный Merchant ID во внешней карте. При отсутствии совпадения пробует каждый указанный префикс, совпавший с началом ID. Затем пробует постфиксы сначала у полного ID, затем у вариантов без префикса.

Префикс/постфикс сравнивается без учёта регистра только на соответствующем краю строки; середина ID не заменяется. Побеждает первое найденное совпадение. Рекурсивного удаления произвольного количества префиксов/постфиксов нет.

Внешние ID при загрузке нормализуются, но заданные префиксы и постфиксы с них не обрезаются. Пример в обратную сторону, где Merchant `123`, а XML `UA123`, этим механизмом не решается.

При нескольких XML первая найденная запись нормализованного ID остаётся в общей карте. Если внешний источник включён, но совпадение товара не найдено, `product.productTypes` становится пустым массивом: автоматического возврата к Merchant product type в этой ветке нет.

Категория меняется только внутри расчёта скрипта. Скрипт не записывает product_type обратно в Merchant; в Products выводятся ID, исключения и метки. По ID `123`, `UA123`, `123_ru` статистика остаётся раздельной.

### Валидация и поведение ошибочных значений

`validateRuntimeSettings_` вызывается после чтения и пересборки Settings, до загрузки каталога:
- Merchant ID должен быть непустым и не равным заглушке.
- Страница Merchant: 1...1000; повторы: 0...10; базовая пауза: 1...120 секунд.
- Размер блока записи: 100...20000; первая строка диагностики не ниже 1.
- Период воронки и периоды NO_SALES/SPEND/TARGET_CPA не меньше 1.
- Исключённые дни, порог кликов, длительности пауз, лимит истории и задержка регистрации неотрицательны.
- Порог problematic не меньше 1.
- Доля цены и порог дорогого CPC строго положительны; допуск CPA неотрицателен.
- URL внешнего XML должны начинаться с HTTP или HTTPS.
- При авторегистрации требуется непустой developer_email.
- Оба выходных custom label должны быть валидными и различаться.
- Поле custom label категорий проверяется при включённом источнике; источник benchmark - при включённой группировке; priority-источник проверяется отдельно.

Генератор не исправляет автоматически неверный смысл числа: 20 вместо 20% остаётся числом 20. Верхнего ограничения 100% на допуск CPA и долю цены текущая runtime-валидация не задаёт. Проверка маржи для расчёта ROAS выполняется в формуле, а не отдельной общей валидацией Settings.

### Служебные переключатели: что остаётся работать

`enable_product_diagnostics=FALSE` оставляет три поля жизненного цикла карантина; не очищает старые остальные метрики. `enable_previous_state_read=FALSE` не отключает чтение этих трёх полей.

`enable_dashboard_data=FALSE` сохраняет старое содержимое DashboardData. `enable_dashboard=FALSE` не удаляет старый Dashboard и не запрещает его формулам реагировать на источники.

`enable_managed_sheet_formatting=FALSE` не является глобальным выключателем оформления. Settings, ProductTypes, Seasonality продолжают собственное оформление. У DashboardData оформление зависит от первоначальной пустоты листа; у Dashboard - от генерации layout.

`enable_sheet_protection=FALSE` пропускает общий проход защиты, но не снимает старые защиты других листов. Seasonality имеет отдельное снятие доступных защит.

`enable_products_write=FALSE` сохраняет старый допфид. При обычном запуске без старых товарных строк вызывается ошибка; это не режим полностью безопасного холостого запуска, поскольку другие записи до этой проверки уже возможны.

`product_diagnostics_start_row>1` не является курсором API или возобновлением расчёта: весь каталог и показатели рассчитываются заново, а затем выбирается хвост для записи полной диагностики.

### Merchant API: загрузка, фильтры и повторы

`getMerchantProducts_` выполняет `Accounts.Products.list` для аккаунта. Он запрашивает не отдельные фиды, а страницы общего списка товаров. После получения каждой страницы последовательно проверяет legacyLocal, data source, feed label и язык; ненужные товары не добавляются в итоговый массив.

В текущем запросе только pageSize и pageToken. Метод Google не имеет параметра фильтра источника до загрузки. Это подтверждено [справкой products.list](https://developers.google.com/merchant/api/reference/rest/products_v1/accounts.products/list). По решению пользователя текущий способ оставлен; переход на Merchant Reports не реализуется.

`merchant_api_retry_count=5` означает максимум шесть попыток страницы. Повторяются распознанные временные ошибки: internal/backend, rate limit/quota, timeout/unavailable и соответствующие коды. Пауза увеличивается линейно: при базе 10 секунд перед следующими попытками 10, 20, 30, 40, 50 секунд. Неповторяемая ошибка или исчерпание попыток прерывает запуск.

Ошибка регистрации Merchant обрабатывается отдельно с сообщением о настройке регистрации. `auto_register_gcp_project` сначала проверяет существующую регистрацию, при необходимости выполняет регистрацию; если Google указал родительский аккаунт, код пробует предложенный аккаунт. Задержка после успешной новой регистрации задаётся в секундах и не выполняется при каждом обычном чтении страницы.

Если после фильтров не осталось товаров, обычный запуск завершится ошибкой до записи Products. Это не команда очистить допфид.

### Сохранение текста комментариев Settings

Комментарии генерируются из кода при пересборке. Ручное изменение только колонки C не сохраняется как пользовательская настройка: для постоянного изменения нужно менять шаблон генератора.

Для служебных полей исходные пояснения сохранены, дополнительные условия дописаны после них. В частности, старые фразы о Dashboard и полной диагностике нужно читать вместе с уточнением, а не отдельно. Для сезонных галочек пояснено ручное продление сезона; для префиксов/постфиксов - направление сопоставления и отсутствие объединения статистики.

## 23. Практические сценарии проверки

### Погоджена відсутність архіву зниклих об'єктів

Користувач погодив не додавати архів товарів і категорій, які зникли з вибірки. Після повернення клієнт перевіряє та відновлює потрібні ручні налаштування. Це прийнята межа відповідальності, а не відкрита задача.

Збереження за ID або шляхом працює, поки попередні дані доступні при читанні листа. Після успішної перебудови без об'єкта його дані можуть бути відсутні вже на наступному запуску. Для Seasonality це ручні сезони й коментар; для ProductTypes — ручний вибір, метки, сезони, цілі, маржа та коментар. Повернений невідомий шлях отримує початкові значення, включно з увімкненою категорією.

Повна діагностика також містить лише поточні товари: дата виходу відсутнього ID не є безстроково архівованою. Скорочений запис трьох полів зберігає старі рядки, тому режими відрізняються. Загальні Settings не скидаються; Priorities зберігає ручний список незалежно від поточної наявності товару.

Для уникнення втрати налаштувань тимчасово недоступний товар має залишатися у вибірці зі сталим ID та шляхом і правдивим статусом наявності. Категорія існує в дереві через шляхи товарів. Зникнення можливе також через фільтри або неповну вигрузку, не лише через ручне видалення. Карантин сам по собі не вилучає товар із Merchant-вибірки.

### Погоджений зміст формули порогів

Формула: threshold = ceil((avgAll + avgPositive) / 2). Умова високого сегмента: є різні позитивні значення, value > avgAll і value >= threshold. Окремо для кліків і показів у benchmark, за рядками без позитивних конверсій.

Користувач підтвердив мотив: нульові товари занижували загальне середнє; середина між двома середніми враховує їх, не дозволяючи їм визначати межу самостійно.

| Крок для кліків 0, 10, 20 | Результат |
| --- | --- |
| Середнє всіх: (0 + 10 + 20) / 3 | 10 |
| Середнє позитивних: (10 + 20) / 2 | 15 |
| Середина: (10 + 15) / 2 | 12,5 |
| Округлення вгору | 13 |
| Класифікація | 0 і 10 — низькі; 20 — високі |

Не змінювати формулу на медіану, звичайне середнє чи поділ асортименту навпіл без окремого погодження. Кліки без показів вважаються статистикою; позитивні конверсії мають пріоритет для етапу продажів.

Этот раздел - справочник способов проверки поведения, не второй список открытых доработок и не утверждение, что все перечисленные сценарии выполнены. Активные и отложенные задачи ведутся только в `merchant_product_control_new_table_test_issues.md`.

### Проверка целей, маржи и процентов

При сравнении читать не только отображение, но и хранимое число/формулу. Для порогов 30% и 20% это 0.30 и 0.20; для маржи 30% это число 30; для Target ROAS 300% - коэффициент 3.

Положительное ручное число Target ROAS должно сохраниться при повторной пересборке. Формульная цель должна следовать марже категории или общей марже. Пустая категорийная цель CPA не должна заполняться числом автоматически, но общая цель участвует в подсветке и построении правил.

Локальный файл `tests/sheet-regressions.cjs` проверяет агрегаты категорий, сохранение целей, формулу, индексы Seasonality, форматы диагностики, положение даты, цветовые группы, отсутствие автозащиты Seasonality, комментарии Priorities, внешнее сопоставление и порядок CPA/ROAS.

### Проверка даты выхода и карантинных сумм

Для товара с наблюдавшимся карантином сравниваются три вещи: прежняя активность, дата последнего выхода и существующие показатели карантинного правила. Общие clicks/cost в начале диагностики для этого сравнения не подходят: они используют другое окно.

Нужен фактический переход из активного карантина в неактивный. Пустая дата у товара, который ещё не вышел, сама по себе не является ошибкой. После выхода дата не должна сдвигаться каждый запуск, а старые клики и расходы до неё не должны возвращаться в суммы правил.

Локальный `tests/quarantine-lifecycle.cjs` проверяет общую дату, перекрывающиеся причины, стабильность даты, удаление старой статистики, задержку доступных дней, общий кэш и возврат обычного окна.
