## Залежності Settings і відновлення

```text
Той самий SPREADSHEET_URL → наявний Settings → читання значень
                                             ↓
                      додати тільки відсутні ключі → validation → розрахунки
```

Код відкриває наявний файл через openByUrl, не створює новий spreadsheet. Settings не перейменовується і не видаляється. У коді звернення до Settings виконуються за назвою; прямі формули ProductTypes і Dashboard шукають ключі через MATCH у A:A та INDEX у B:B. Нові ключі додаються після останнього зайнятого рядка, тому адреси старих клітинок і named ranges не переміщуються. Код не перебудовує named ranges. Existing validations інших клітинок не очищаються, захисти Settings не переносяться на інший лист.

За збою після додавання рядків повторний запуск перечитує фактичні ключі: дублікати не створюються, validation може бути відновлена. Значення старих рядків не стираються на жодному етапі міграції. Це перевірено через ін'єкцію збою в локальному mock; збій Google Sheets і конкурентні запуски потребують live-перевірки. Одночасні запуски під час міграції не запускати.

Архів Settings не потрібен. Перед тестом користувач зберігає резервну копію/версію; робочий файл і його URL залишаються тими самими. Довільні клієнтські формули й named ranges не були доступні для інспекції: перевірити їх на обраному проекті до/після.

## Джерела URL категорій

Перевірено код: Merchant reader використовує productTypes як назви; зовнішній XML parser збирає пари `id + product_type`. У цих значеннях немає гарантованого URL категорії. `link` Merchant — сторінка конкретного товару, не категорії. Назва категорії або обрізання товарного URL не дають достовірного mapping.

Наявні клікабельні назви підтягуються через getRichTextValues/getLinkUrl; явний category_url має пріоритет. HTTP(S)-формат перевіряється, але це не перевірка семантичної відповідності сторінки. Для відсутніх адрес потрібне підтверджене джерело: експорт категорій CMS із шляхами та URL або конкретний сайт для перевірки його меню/структурованих даних. Краулер і вигадані slug не додані.

Офіційні джерела: [ProductAttributes](https://developers.google.com/merchant/api/reference/rest/products_v1/ProductAttributes), [product_type](https://support.google.com/merchants/answer/6324406?hl=en), [link](https://support.google.com/merchants/answer/6324416?hl=en), [RichTextValueBuilder](https://developers.google.com/apps-script/reference/spreadsheet/rich-text-value-builder), [Sheet API](https://developers.google.com/apps-script/reference/spreadsheet/sheet).

## ProductDiagnostics проти QuarantineLog

Спостереження коду, а не висновок про клієнтський випадок:

- `ProductDiagnostics` — поточний стан каталогу; частковий/вимкнений повний writer оновлює лише ID, активність карантину і дату виходу. Інші поля можуть бути старішими.
- `QuarantineRegistry` записується раніше Diagnostics і зберігає активні записи.
- `QuarantineLog` — агрегат `id, quarantine_count, last_added, problematic`, а не журнал кожної події або причини. Він сортується за count за спаданням, потім за ID. `quarantine_log_max_rows` обрізає цей список. Чинний опис налаштування про «останні події» неточний; алгоритм у цьому пакеті не змінювався.
- За ліміту 1 товар із count=10 витісняє активний товар із count=1. Це відтворено локально; така розбіжність очікувана.
- Збій між записами, dashboard-only, старий частковий Diagnostics, ручні зміни або reset — можливі причини для перевірки, не встановлений діагноз.

Для реального випадку зберегти: точний ID та нормалізований ID, час/часовий пояс запуску, рядок Diagnostics з конкретним полем, Registry, Log, settings ліміту та reset/diagnostics/dashboard-only, журнал виконання. Перевірити, чи йдеться про quarantine_active=YES зараз або про історичний count/reason. Після цього визначити, чи рядок зобов'язаний залишатися в обмеженому Log.

## Один спільний цикл тестування

1. Обрати один проект; URL таблиці у цій задачі не надано. Не запускати паралельно старий і новий скрипт.
2. Зберегти код v1.2.1, налаштування, скріншоти/експорт Settings, ID файла й gid листів, named ranges та приховані колонки. Зупинити автоматичне отримання тестованого допфіда до перевірки. Це дія користувача.
3. Взяти script.js з робочої гілки, вказати чинний SPREADSHEET_URL. Google Ads Preview **не гарантує відсутності записів SpreadsheetApp**; навіть preview цієї версії може оновити таблицю.
4. Запустити один раз; перевірити незмінні URL/gid, старі значення/формули/невідомі ключі Settings та новий checkbox внизу. Повторити: немає дублів, формат користувача й приховані колонки збережені.
5. Перевірити priority: різні значення Priorities, ProductTypes і Merchant; `product_types_sheet` бере категорію, порожня дочірня — батька, без правила — порожньо. `none` дає порожню діагностичну priority навіть за заповнених джерел.
6. Для output=none на старому фіді очікувати `Products status: PRIORITY_MIGRATION_REQUIRED`. Старий фід усе ще містить priority. **Не вважати цей тест завершенням міграції.** Після окремого рішення: зберегти стару п'яту колонку поза допфідом, перевірити її використання Merchant/іншими задачами, погодити її видалення/очищення та правила джерел у Merchant. Лише після цього повторити й очікувати 4 колонки та `WRITTEN`. Автоматично це не виконується.
7. `enable_products_output=false`: перевірити повністю порожній Products при обох значеннях enable_products_write, включно dashboard-only. Dashboard та діагностика продовжують працювати, якщо ввімкнені. Повернути true та write=true — дані відновлюються. Порожній допфід не гарантує негайного скасування раніше застосованих міток у Merchant.
8. CR: звірити категорію з сумою її товарів за ті самі 30 днів; перевірити 0 кліків, 0 конверсій, дробові конверсії і батьківську категорію. Заповнити/імпортувати підтверджені URL: кожне видиме ім'я веде саме у свою категорію, пропусків немає.
9. На тестових ID перевірити кожну причину карантину, комбінацію причин, одночасне категорійне/сезонне виключення, збереження ID і відновлення етапу після виходу. Аналітичний етап Diagnostics не підміняється feed-міткою.
10. **Перед обробкою нового допфіда** користувач перевіряє всі Standard Shopping/PMax: кожне карантинне значення, включно комбінаціями, відокремлене й виключене, «Усі інші товари» не включає карантин. Потім перевірити Merchant processing, відсутність показів і доступність історії товару за тим самим ID. Скрипт кампанії не змінює.
11. Перевірити protection=false з наявним захистом, true з правами виконавця, чужий range protection і недоступний запис. За відмови запису перевірити права конкретного листа/діапазону та повний текст помилки; не підміняти її «авторизацією Ads».
12. Спостерігати багатоденний цикл: вхід → повторний запуск без продовження active_until/count → природний вихід → нове вікно статистики після виходу → повторний вхід. Один запуск це не доводить.

Цей Unified не має waterfall RunState/RunLog. Перевіряти журнал виконання Google Ads, QuarantineRegistry, QuarantineLog і ProductDiagnostics. Очікувані нові повідомлення: `Products status: WRITTEN`, `DISABLED_EMPTY`, `PRIORITY_MIGRATION_REQUIRED`, `CATEGORY_URL_MISSING`. Останні два потребують дій, а не означають повну готовність пакета.

## Відкат

Зупинити новий розклад і обробку допфіда на час перевірки. Повернути script.js з тегу v1.2.1 та той самий SPREADSHEET_URL; звірити збережені налаштування перед запуском. Старий код перебудовує Settings і може прибрати нові ключі — спочатку зберегти їх. За потреби відновлювати дані/версію в тому самому файлі, не підміняти файл новою копією; врахувати зміни карантину після резервної точки. Перевірити Merchant після старого фіда: повертаються карантинні excluded_destination. Не скасовувати виключення карантинних міток у кампаніях, поки перехід не перевірено. Історію Git не переписувати.

Новий package-12 перевіряє міграцію після збою, джерела priority, стару колонку без записів, загальне очищення, CR, URL/видимість, feed-мітку карантину/вихід, окремі виключення і ліміт історії. Це mocks і розрахунки, не підтверджений запуск Google Ads/Sheets/Merchant.
