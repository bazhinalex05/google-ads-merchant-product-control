# Unified Merchant Product Control: полная инструкция по установке

## 1. Чек-лист перед настройкой

Перед настройкой скрипта нужно знать следующую информацию. Опциональные параметры приведены отдельно ниже.

### Каталог и поля

| Параметр | Ответ |
| --- | --- |
| ID Merchant Center | |
| ID рабочих фидов | |
| Поле категорий | |
| Источник benchmark* | |
| Источник приоритета* | |
| Свободный custom label воронки | |
| Свободный custom label приоритета | |

*Benchmark — группа, внутри которой скрипт сравнивает товары между собой по статистике и рассчитывает сегменты воронки. При включённой группировке статистика другой benchmark-группы не влияет на пороги первой. Это нужно, чтобы сравнивать похожие по смыслу товары между собой. Укажите поле, из которого брать группы: например, product_type_l1 группирует товары по первому уровню категории.

*Источник приоритета — поле Merchant, из которого скрипт читает уже назначенный товару приоритет клиента. Если приоритет задан вручную на Priorities по ID или на ProductTypes для категории, он имеет преимущество перед значением из Merchant.

Разница в назначении: benchmark использует сам скрипт, чтобы рассчитывать сегменты воронки внутри групп похожих товаров. Приоритеты нужны нам для управления рекламой в Google Ads с учётом интересов клиента: по меткам приоритета можно разделять товары и задавать для них разные рекламные настройки, а при разделении на кампании — разные бюджеты. Настройки и бюджеты задаёт специалист в Google Ads; сам скрипт их не меняет, а передаёт метки приоритета через наш допфид.

Источник чтения приоритета и поле записи приоритета могут совпадать. Например, клиент уже передаёт приоритеты через дополнительный фид в custom_label_4 или эта метка уже заполнена другим способом. Скрипт читает приоритет из custom_label_4 в Merchant и записывает итоговый приоритет в колонку custom_label_4 на листе, который будет нашим дополнительным фидом. Он не записывает его напрямую в Merchant: результат применяется после обработки допфида. Разными должны быть два выходных поля нашего допфида: этап воронки и приоритет.

### Карантины

Каждое правило карантина можно включить или выключить отдельно.

Для каждого карантина задаются:

- **Период проверки** — за какой период проверяется статистика товара.
- **Срок карантина** — на сколько дней товар исключается из рекламных показов.

Дорогой клик всегда проверяется за вчера. У него период проверки не настраивается.

Виды карантина отличаются условием срабатывания:

- **Клики без продаж:** клики выше порога, конверсий нет.
- **Перерасход относительно цены:** расход достиг заданной доли цены; нет конверсий или их ценности, либо расходы выше ценности конверсий.
- **Дорогой клик:** средний CPC за вчера выше порога.
- **Продажи с дорогим CPA:** есть конверсии, а CPA превышает целевой на заданный процент.

| Параметр | Ответ |
| --- | --- |
| Клики без продаж, шт. | Указать количество кликов, выше которого товар без конверсий отправляется в карантин. |
| Расход от цены, % | Указать процент от цены товара, при достижении которого проверяется условие перерасхода. |
| Средний CPC | Указать стоимость клика, выше которой средний CPC за вчера приводит к карантину. |
| Превышение Target CPA, % | Указать допустимое превышение целевого CPA в процентах, выше которого товар отправляется в карантин. |

По умолчанию период проверки — 30 дней без сегодня и вчера, для дорогого клика — вчера. Срок карантина — 7 дней. Периоды и пороги настраиваются в Settings с указанным исключением для дорогого клика.

### Опциональные параметры

Без этих данных скрипт может работать. Их заполнение позволяет учитывать экономику и приоритеты клиента: сравнивать CPA с целями, применять карантин дорогого CPA и автоматически передавать назначенные приоритеты в допфид.

| Параметр | Пояснение и пример |
| --- | --- |
| Общий Target CPA | Желаемая средняя стоимость заказа, по которой клиент согласен получать заказы. Например, 350 грн за заказ. Это цель клиента, а не фактический средний CPA аккаунта. |
| Target CPA категорий | Попросите клиента указать целевую стоимость заказа для каждой категории, где он её знает. Например: палатки — 500 грн, термобельё — 200 грн. Значения заполняются на ProductTypes; если категорийная цель не задана, применяется общая. |
| Маржа клиента, % | Доля цены продажи, которая остаётся после себестоимости, до рекламных расходов. Например: цена 1 000 грн, себестоимость 700 грн, остаток 300 грн — маржа 30%. Не путать с наценкой: в этом примере наценка относительно себестоимости составляет около 43%. Для настройки указываем 30. |
| Маржа категорий, % | Если клиент знает маржинальность товаров по категориям, попросите указать процент для каждой такой категории на ProductTypes. Например: палатки — 25%, термобельё — 40%. Если отдельное значение не задано, используется общая маржа клиента. |
| Список приоритетов клиента | Список из двух колонок: ID товара и приоритет. Например: 12345 — приоритет 1; 67890 — приоритет 2; 24680 — приоритет 3. Список можно добавить на лист Priorities в колонки id и priority_group. |

Если Target CPA или маржа неизвестны, оставьте соответствующие поля пустыми. Без общей и категорийной цели карантин дорогого CPA не сработает.

### Примечания

Категории для работы выбирает клиент на ProductTypes после создания листа. Сезонность категорий и товаров также заполняет клиент.

Период воронки по умолчанию — 14 дней, включая сегодня. Этот же период используется для расходов на дашбордах, включая расходы активных карантинных товаров.

## 2. Порядок установки

### Шаг 1. Добавить код и таблицу

Откройте раздел скриптов в рекламном аккаунте клиента, создайте скрипт и вставьте актуальный код. Создайте пустую Google-таблицу. Замените значение SPREADSHEET_URL в коде её полной ссылкой, сохранив кавычки. Остальные настройки будут в Settings.

Перед первым запуском включите доступ к Merchant API:

1. Справа вверху над редактором кода, рядом со ссылкой «Документация», нажмите **«Расширенные API»** (в английском интерфейсе — **Advanced APIs**).
2. В открывшемся окне включите **Merchant API**. Для работы скрипта нужны службы **Products** и **Accounts**.
3. Подтвердите изменения в окне. Сохраните скрипт и нажмите **«Авторизовать»** на жёлтой полосе над кодом, если разрешения ещё не предоставлены. Предоставьте запрошенные разрешения.

### Шаг 2. Создать Settings первым запуском

Запустите скрипт. Он создаст Settings и остановится с просьбой заполнить Merchant ID. Для первого запуска с незаполненным ID это ожидаемо. Других рабочих листов на этом этапе ещё нет.

### Шаг 3. Заполнить Settings сверху вниз

Меняйте значения и галочки, не названия параметров. Пройдите разделы в том порядке, в котором они расположены на Settings. Названия ниже приведены как на листе.

1. **Основні налаштування.** Укажите ID Merchant Center, общий Target CPA и маржу клиента. Если Target CPA или маржа неизвестны, оставьте соответствующие поля пустыми.
2. **Фільтри фідів і Merchant API.** Укажите ID фидов, с которыми работаем. При необходимости задайте ограничения по метке фида и языку.
3. **Увімкнення функцій.** Для базового запуска здесь можно ничего не менять: фильтр категорий, воронка и карантин по умолчанию включены. Сезонность по умолчанию выключена; включайте её, если она нужна. Категории и сезоны товаров клиент заполнит после создания остальных листов.
4. **Етапи воронки.** Укажите, из какого поля скрипт будет читать benchmark-группу и из какого — приоритет товара. Отдельно выберите два разных выходных custom label для нашего допфида на листе Products: в один скрипт запишет итоговый этап воронки (Funnel Stage), в другой — группу приоритета. Benchmark используется только для расчёта и в допфид не записывается.
5. **Сезонність.** Пока клиент не отметил сезоны категорий или отдельных товаров, этот блок не трогайте. После заполнения сезонности и включения её фильтра здесь галочками выбираются сезоны, товары которых разрешены сейчас, независимо от календаря. Например, включили «лето» — товары с отмеченным летним сезоном проходят сезонный фильтр сейчас, даже если по календарю осень, зима или весна. Можно разрешить несколько сезонов одновременно. Скрипт использует выбранные галочки, а не добавляет текущий календарный сезон автоматически. Другие ограничения товаров сохраняются.
6. **Категорії товарів.** Если сайт или CMS клиента передаёт дерево категорий в стандартном product_type, здесь ничего не меняйте. Альтернативный атрибут настраивайте только если дерево категорий передаётся в другом поле, например в custom label: включите этот источник и укажите нужное поле.
7. **Карантин.** Включите выбранные правила и задайте их пороги, периоды проверки и сроки карантина.
8. **Службові налаштування скрипта.** При установке ничего не меняйте. Тестовый сброс карантина reset_quarantine оставьте выключенным. Он нужен только для полной очистки карантинов и их истории, например после тестирования настроек. Для очистки включите галочку и выполните обычный запуск скрипта, затем снимите её. Пока галочка включена, карантины очищаются при каждом запуске и заново не назначаются.

### Шаг 4. Создать остальные листы

После того как заполнили Settings, запустите скрипт повторно. После успешного запуска появятся остальные рабочие листы и товары.

На **ProductTypes** отметьте галочками категории, которые нужны нам для рекламы. Согласуйте выбор с клиентом или попросите клиента самостоятельно проставить галочки. Отбор применяется при включённом фильтре категорий.

На **ProductTypes** также задаётся сезонность категорий. Если категория и все товары внутри неё относятся к одному сезону или набору сезонов, отметьте соответствующие галочки здесь.

Если отдельным товарам внутри категории нужны другие сезоны, попросите клиента открыть **Seasonality** и проставить для них индивидуальные галочки. У этих товаров отмеченные вручную сезоны заменят сезонность категории.

Коли сезонність вимкнена, Seasonality не заповнюється і не перезаписується; наявні дані зберігаються. Якщо лист порожній, виберіть активні сезони в Settings, увімкніть enable_seasonality_filter та запустіть скрипт. Після розмітки товарів повторіть запуск і перевірте виключення до підключення допфіда. Підсумкові сезони розраховує скрипт без формул: зміни галочок застосовуються після запуску, не миттєво.

**Уточнение настроек по категориям.** Если нужные значения и источники уже настроены в Settings и подходят для категории, повторно заполнять их на ProductTypes не нужно. Здесь указываются данные, которые не заданы в Settings, либо более точные настройки отдельных категорий:

- **Target CPA:** желаемая клиентом стоимость заказа для этой категории. Заменяет общий Target CPA из Settings для товаров категории.
- **Процент маржи:** маржинальность товаров этой категории до рекламных расходов. Заменяет общую маржу из Settings.
- **Benchmark label:** конкретная группа сравнения для категории. Используется вместо группы, прочитанной из источника, выбранного в Settings.
- **Priority label:** конкретный приоритет для категории. Используется вместо приоритета, прочитанного из источника, выбранного в Settings.

Если уточнения не нужны, оставьте эти поля пустыми: продолжат применяться общие значения и выбранные источники. Повторно заполнять те же данные не требуется. В Settings для benchmark и приоритета выбираются поля-источники; здесь задаются сами метки конкретной категории.

**Индивидуальные приоритеты товаров — тоже необязательно.** Если клиент передал список «ID товара — приоритет», его можно внести на Priorities. Значение по ID важнее приоритета категории и значения из Merchant. Если выбранный в Settings источник уже содержит нужные приоритеты, дублировать их на Priorities не нужно.

Выполните ещё один запуск для применения ручных настроек.

**До завершения настройки и проверки не добавляйте эту таблицу в Merchant Center как дополнительный фид.** Иначе незавершённые или ошибочные настройки могут изменить метки и исключения товаров в Merchant и нарушить работу рекламных кампаний.

### Шаг 5. Проверить таблицу

Проверьте состав Products, причины исключений в ProductDiagnostics, активные записи QuarantineRegistry и сводку Dashboard. DashboardData содержит детализацию сводки.

**Обратите внимание:** расходы карантинных товаров на дашборде — это расходы за период воронки (по умолчанию 14 дней, включая сегодня) по товарам, которые сейчас находятся в активном карантине, то есть поставлены на паузу. Это не доказанная экономия: показатель отражает уже понесённые расходы, а не сумму денег, которую удалось сэкономить.

Пауза для малоэффективных товаров позволяет потенциально сократить дальнейшие расходы на них или направить бюджет на другие товары. Показанная сумма помогает оценить масштаб прежних затрат на этот ассортимент, но не гарантирует, что именно такая сумма будет сэкономлена или перераспределена: результат зависит от дальнейшей работы рекламных кампаний.

### Шаг 6. Подключить Merchant

**Перед подключением таблицы** проверьте, что custom label, используемые на Products для этапа воронки и приоритета, не заняты правилами фида клиента, которые будут конфликтовать с записью наших значений. Согласованное чтение и запись приоритета в одну метку допустимо, как описано выше.

Если выходные метки заняты, вернитесь в Settings, раздел «Етапи воронки», и выберите свободные custom label в funnel_stage_output_attribute и priority_output_attribute. Повторно запустите скрипт, чтобы он обновил Products, и только затем подключайте таблицу.

Добавьте эту Google-таблицу в Merchant Center как дополнительный источник данных (допфид) для нужного основного источника.

**Products обязательно должен быть первым листом:** при подключении допфида через Google-таблицу Merchant читает первый лист. Скрипт автоматически перемещает Products на первое место, но перед подключением проверьте порядок листов и не переносите другой лист перед ним.

### Шаг 7. Проверить применение и расписание

После обработки допфида убедитесь, что у соответствующих ID товаров в Merchant появилась информация из нашей таблицы и она соответствует данным допфида: этап воронки, приоритет и исключения.

После добавления таблицы проверьте, во сколько обновляется основной фид. В нашей схеме установки задайте обновление дополнительного фида **ровно на один час раньше основного**. Например, если основной фид обновляется в 06:00, дополнительный должен обновляться в 05:00. Сверяйте время в одном часовом поясе.

Это расписание обновления допфида в Merchant, а не расписание запуска самого скрипта в Google Ads.

**Для самого скрипта в Google Ads установите ежечасный запуск.** При каждом успешном запуске он обновляет рабочую таблицу, а Merchant по настроенному ежедневному расписанию забирает из неё данные допфида.

Такой режим снижает влияние разовых технических сбоев Google: если один запуск прервался, через час скрипт запустится снова и при успешном выполнении обновит данные. Поэтому единичный сбой не обязательно нарушит ежедневное обновление допфида. Повторяющиеся ошибки нужно проверять: почасовое расписание не устраняет постоянную неисправность и не гарантирует обновление к моменту загрузки допфида.
